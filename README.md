# 企業情報 自動取得 PoC

**①企業名そのものの自動収集（発見層）→ ②公式HPのURL → ③電話番号 → ④採用担当者名 を自動取得する**実装です。
企業名リストを持っていれば②〜④だけを回せますし、企業名すら無ければ**キーワード（業種・地域）や一覧ページから企業名自体を自動収集**できます。
入出力は **Google スプレッドシート / GAS / ローカルCSV**。スクレイピング本体はGASでは動かせないため Node＋Playwright で実行し、**リストの読み込みと結果の書き戻し**をスプレッドシートが担います。

## 起点は3通り（どれでもOK）
1. **企業名すら無い** → `--discover "<キーワード>"`（業種・地域など）または `--discover-url <一覧ページURL>` で企業名を自動収集 → そのまま②〜④へ。
2. **企業名リストはある** → A列に企業名（URLは任意）。URLが空なら企業名から自動発見。
3. **URLも分かっている** → A列＋B列に記入。検索をスキップして高速・確実。

## 設計方針（外部AI API 不使用・ローカル処理のみ）
**Anthropic 等の外部AI APIは一切呼び出しません。** 課金もネットワーク先での処理も発生しません。全項目をローカルの正規表現・スコアリング・人名判定で取得します。
- **URL発見**：Bing の検索結果HTML（**APIキー不要・無料**）から候補を取得 → 求人媒体・SNS・企業DBを除外 → 「公式コーポレートサイトらしさ」をスコアリング → 上位を実際に取得して**企業名一致を検証**してから採用。
- **電話番号**：`tel:` リンク＋正規表現で抽出。`TEL/代表/お問い合わせ` 近接で加点、`FAX` 近接は減点、法人番号・登録番号など長い数字列の誤検出を除外。
- **採用担当者名**：本文の正規表現（「採用担当：氏名」等）＋**人名らしさ判定**（役割語・組織語・見出し語を除外）で抽出。

## なぜ媒体が「公式企業サイト」なのか
- **合法性が最も安全**：企業自身の公開ページを robots.txt 遵守・低速で読むだけ。第三者プラットフォームのアンチボットや認証回避を伴わない。
- **信号が強い**：電話番号・採用/人事担当の氏名が「お問い合わせ」「採用情報」「会社概要」に載りやすい。
- **技術的に扱いやすい**：多くは静的HTMLで取得でき、必要時のみブラウザ描画にエスカレーションすればよい。

## スプレッドシートの列レイアウト
1行目はヘッダ。**A列（企業名）を用意するだけ**で動きます。B列（URL）は任意で、空なら企業名から自動発見します。C列以降は本ツールが自動で書き戻します。

| 列 | 内容 | 記入者 |
|---|---|---|
| A | company_name（企業名・**必須**） | あなた |
| B | homepage_url（公開トップページURL・**任意**） | あなた（空欄なら自動発見。分かっていれば入れると高速・確実） |
| C〜R | status / resolved_url / phone / name / role / department / confidence / url_source / phone_source_url / name_source_url / evidence / engine / pages_checked / elapsed_ms / error / updated_at | ツールが書き戻し |

- `status` は **採用担当者名** の HIT / MISS（加えて NO_URL / SKIP_ROBOTS / ERROR）。URL・電話の取得可否は `resolved_url` / `phone` 列の有無で分かります。
- `url_source` は URL の出所：`input`（入力）/ `search+verified`（検索＋企業名一致を確認）/ `search(unverified)`（検索のみ・要目視確認）。
- 再実行時に `ONLY_PENDING=true` にすると **status空欄の行だけ**処理します（差分更新・再開に便利）。

## 接続方式は2つ（どちらか選択）

### 方式①：Google Sheets API（サービスアカウント）— 自動実行向き・推奨
1. GCPでプロジェクト作成 → **Google Sheets API を有効化**
2. **サービスアカウント**を作成 → 鍵（JSON）を作成・ダウンロード（例：`service-account.json` をプロジェクト直下に置く）
3. 対象スプレッドシートを、サービスアカウントのメール（`xxxx@xxxx.iam.gserviceaccount.com`）に **「編集者」で共有**
4. `.env` に設定：
   ```
   SOURCE=sheet
   SHEET_ID=<スプレッドシートID>      # URLの /d/ と /edit の間
   SHEET_TAB=Sheet1
   GOOGLE_APPLICATION_CREDENTIALS=./service-account.json
   ```

### 方式②：GASウェブアプリ橋渡し — GCP不要（GAS運用に慣れている場合）
1. 対象スプレッドシートを開く → **拡張機能 → Apps Script**
2. `gas-bridge/Code.gs` を貼り付け（必要なら `TAB` をシート名に変更）
3. **デプロイ → 新しいデプロイ → ウェブアプリ**（実行＝自分／アクセス＝全員）
4. 発行された `/exec` のURLを `.env` に設定：
   ```
   SOURCE=gas
   GAS_URL=https://script.google.com/macros/s/XXXXX/exec
   ```

### 発見モード（企業名そのものを自動収集）
```bash
# キーワード（業種・地域など）から企業名を収集し、そのままURL/電話/担当者まで取得（結果はCSV）
node src/index.js --discover "渋谷 システム開発 会社" --limit 20

# 企業一覧ページ（商工会名簿・会員一覧・まとめ記事など）から企業名を収集
node src/index.js --discover-url "https://example.org/members" --limit 50

# 企業名リストだけ作る（C列以降は取得しない）。出力CSVをそのまま --input に使える
node src/index.js --discover "大阪 製造業 企業 一覧" --discover-only --out companies.csv
```
- 発見モードの結果は**既存シートを上書きしないようCSVに出力**します（`--out` で変更可）。
- **収量はソース依存**：多くのWebページは「株式会社」を省いて製品名・ブランド名で記載するため、`おすすめ◯◯` 系の記事は法人名が少なく収量が落ちます。**会社名が法人格付きで列挙される一覧（会員名簿・企業ディレクトリ・「◯◯ 会社 一覧」）ほど高収量・高精度**です。精度優先のため、確信が持てない断片は採用しません（ゴミを後段に流さない）。

## 出力（4項目）
- **企業名 → 公式URL → 電話番号 → 採用担当者名** を各行 C〜R列に直接書き戻し（出所・根拠・取得日時付き）
- コンソールに **公式URL発見率 / 電話番号取得率 / 採用担当者名取得率**、平均確度・処理時間を集計表示
- 書き戻しに失敗した場合は `results.fallback.csv` に退避（結果を失わない）

→ セグメント（業種・規模・ベンチャー比率）ごとにシート／タブを分けて回すと、**セグメント別の各取得率**がそのまま取れます。

## 処理の流れ
0. **発見層（任意）** `src/discover.js`：キーワード or 一覧URLから企業名を自動収集（Bing検索結果＋上位ページの構造要素から法人格付き社名を抽出）。
1. **URL発見** `src/search.js`：入力URLがあれば使用。無ければ企業名でBing検索 → 候補スコアリング → 上位を取得して企業名一致を検証。
2. **巡回** `src/fetch.js`：トップを取得し、ナビから会社概要/お問い合わせ/採用ページを発見。リンクが無ければ定番パス（/company, /contact, /recruit …）と corp. サブドメインを推測補完。
3. **抽出** `src/phone.js`（電話・正規表現）＋ `src/extract.js`（担当者名・正規表現＋人名判定。**外部AI API不使用**）。
4. **検証ゲート** `src/validate.js`：担当者名は人名らしさ＋採用/人事ロール＋確度閾値を通過したものだけHIT。
5. **集計・書き戻し** `src/metrics.js` / `src/io-common.js` ＋ 各I/Oアダプタ。

## セキュリティ / データ取扱（重要）
- 本リポジトリは**個人情報・企業リスト**を扱う。取扱ルール・暗号化・コミット時ガードは **[SECURITY.md](SECURITY.md)** を参照。
- **clone直後に必ず** `npm install && npm run secure:setup` を実行（pre-commitガードを有効化）。
- 企業リスト/個人情報は `data/` 等（既定で `.gitignore` 済み）に置き、共有は `npm run encrypt:lists`（暗号化ボールト）経由で。

## 法令・マナー（重要）
- robots.txt と各サイト規約を尊重し、**公開ページのみ**を対象にする（認証回避はしない）。
- 取得した担当者名は**個人情報**。利用目的の特定・適正取得・オプトアウト対応を前提に運用すること。
- `.env` の `USER_AGENT` を連絡先付きに設定し、`POLITE_DELAY_MS`/`CONCURRENCY` を過負荷にならない値で。
- 本コードは検証用であり、**法的助言ではありません**。運用前に規約・関連法令の最終確認を。

## 精度の限界（重要・既知）
- **発見層の収量はソース依存**：法人格（株式会社等）付きで社名が列挙されるページほど高収量。製品名・ブランド名だけの記事は収量が落ちます。確実な断片のみ採用するため、ひらがな始まりの一部社名などは取りこぼすことがあります（精度優先）。
- **同名企業の取り違え**：企業名だけでは、よく似た社名の別企業の公式サイトを掴むことがあります。`url_source` が `search(unverified)` の行や、規模に対して不自然なドメインは**目視確認**を推奨。確実な行はB列にURLを入れて再実行してください。
- **担当者名の精度**：氏名抽出はローカルの正規表現＋人名判定で行うため、定型的な表記（「採用担当：氏名」等）は拾えますが、文章中に埋もれた氏名や独特なレイアウトは取り逃すことがあります（**外部AI APIは使いません**）。
- **大企業のコーポレート分離**：採用/会社情報が別サブドメイン（例 corp.example.co.jp）にある場合に対応済みですが、巡回ページ数 `MAX_PAGES_PER_SITE` 内で見つからないと電話を取り逃すことがあります。

## チューニング
- `SEARCH_ENGINE`：`bing`（既定）/ `duckduckgo`。環境により片方が弾かれることがあるので切替可能。
- `MAX_PAGES_PER_SITE`：巡回ページ数。増やすと電話/担当者の取得率↑・所要時間↑。
- `CONFIDENCE_THRESHOLD`：上げると担当者名の精度↑/取りこぼし↑。
- 担当者名の語彙（役割語・非人名ブロックリスト）は `src/extract.js` / `src/config.js` で調整可能。

## 次のステップ（Phase 1）
1. 発見層の高度化：gBizINFO（法人番号・無料トークン）など構造化ソースと併用し、業種・地域での網羅的な企業名収集と収量・精度の両立。
2. 同名企業対策：所在地・業種などの補助シグナルで候補を絞り込み、取り違えを低減。
3. 媒体ワーカーを追加（PR TIMES / Wantedly 等）し、**並列レース＋first-validated-hit cancel** 化。
4. 全MISS時の**架電確認→スプレッドシート書き戻し→次サイクル昇格**ループを実装。

# テレアポ分析システム（架電録音・架電分析）

リスト作成の下流にあたる**架電フェーズの運用と分析**を、ローカルWeb画面に実装したものです。エントリは [`src/telapo-ui.js`](src/telapo-ui.js)。`email-ui.js` と同じ「**Node標準httpのみ・依存追加なし**」の流儀で、**完全ローカル・外部API不使用**で動きます（録音はブラウザ内、文字起こしは手入力）。

```
npm run telapo            # 運用画面を起動 → http://localhost:5179 をブラウザで開く
npm run telapo:dashboard  # 架電台帳(JSONL)を集計してダッシュボードを標準出力へ

npm run test:telapo       # 録音・分析・台帳・集計ロジックの単体テスト
```

## 中核：架電録音 → 架電分析（運用フロー）
1. **架電録音**：ブラウザのマイクで通話を録音（`MediaRecorder`。localhostは安全なコンテキスト扱いでマイク可）、または既存音声（mp3/wav/m4a/webm/ogg/aac）をアップロード → `data/recordings/<id>.<ext>` へ保存。
2. **文字起こし**：手入力（別STTツールの結果を貼付してもよい）。※完全ローカル方針のため音声認識は外部に投げません。
3. **架電分析（規則ベース・ライブ）**：コール結果と文字起こしから、`talk-analysis.js` の規則辞書で
   - **断り理由**（お断り時）：`検討時期が先`／`既存ツール・他社ATSで充足`／`予算なし`／`LINE方針・セキュリティNG` など11分類
   - **アポ獲得トーク要素**（複数該当可）：`母集団形成`／`LINE連携ATSの提案`／`つなぎ止め・歩留まり改善`／`料金・費用対効果` など10要素

   を自動判定し、オペレーターが確認・上書きできます。
4. **架電台帳**：`data/telapo/calls.jsonl` に **1架電=1行** で追記（クラッシュ・並行に強い追記専用ログ。更新/削除は後勝ち/tombstone）。
5. **分析ダッシュボード**：台帳を集計して **接続ファネル（架電→接続→アポ/フォロー/お断り）／コール結果分布／断り理由／アポ獲得トーク要素の出現率／語彙lift（アポ÷お断りの出現率＝トークの決定要因）／オペレーター別成績** を可視化。

## 楽に分析する（自動判定・ワンクリック・音声認識）
入力の手間を減らす2つの仕掛けを載せています。

- **結果の自動判定＋ワンクリック分類（完全ローカル）**：文字起こしを入れると `suggestResult()` が**コール結果を自動推定**して大きな結果バナーで提示し、プルダウン相当のチップを先回り選択（違えばクリックで修正）。**断り理由は1クリック（単一選択）／トーク要素はクリックで複数選択**でき、規則が検出した候補は `◎` 印で先に選択済み。**タイピングせずクリックだけで分類が完了**します。
  - 自動推定は**要約メモではなく“実際の会話文（話し言葉）”に当たるよう重み付きスコア方式**で判定します。「一度お話を…来週水曜14時いかがですか→大丈夫ですよ」「じゃあ一回聞いてみようかな…伺わせていただきます」のような**自然なアポ取りの言い回し**もアポ獲得として拾います。逆に「来月は忙しいので今はいいです。また今度」のように**日付が出ても断り**のケースはアポに誤爆させません（会う/日時の約束シグナルが無い日付だけでは加点しない）。話し言葉25ケースの実測で結果判定 25/25。
  - オペレーターが手で触った項目は自動判定で上書きしません。分析は文字起こし＋メモの本文に対して走るので、**録音だけで文字起こしが無いと分析は空**になります（下記の音声認識ON、または手入力／貼付で本文を用意してください）。
- **音声認識で文字起こし自動入力（任意トグル・既定OFF）**：チェックを入れて録音を開始すると、ブラウザの音声認識（Web Speech API・日本語）が**文字起こしを自動入力**し、そのまま上記の自動判定が走ります。**※ブラウザ内蔵のクラウド認識を使うため通信が発生します（完全ローカルからは外れます）。Chrome / Edge 推奨**。非対応ブラウザではトグルが自動で無効化され、従来どおり手入力／貼付で分析できます（既定はローカルのまま）。

## 設計：BALES後追い分析と規則を共用
断り理由・トーク要素・語彙liftの規則辞書は [`src/talk-analysis.js`](src/talk-analysis.js) を**単一の真実の源**とし、過去データの後追い分析 [`src/analyze-talk-rejection.js`](src/analyze-talk-rejection.js)（BALES 22,892件・接続後の断り理由/アポトーク傾向を集計）と、本システムのリアルタイム運用が**同一ロジック**を使います。つまり「過去22,892件で効くと分かったトーク」と「今日の架電」を同じ物差しで測れます。

```

[L2 発掘]  企業選定          : gBizINFO(あれば) / Bing発掘(既存)        src/discovery.js
[L2 名寄]  法人番号/代表者   : 国税庁 + gBizINFO(あれば・任意)          src/nta.js, src/gbiz.js
[L3 担当]  採用担当者レース  : Gemini(あれば) / 正規表現(既存)          src/recruiter.js（+ fetch/extract/validate）

[L5 出力]  Tier/架電呼称/出力 : 担当者マスタ(Sheet upsert + CSV)         src/score.js, src/master-io.js
           司令塔            :                                          src/pipeline.js, src/app.js
```

## 思想：キー無しでも動き、キーがあれば点火する
**現状APIキーがゼロでも**、`discoverUrl（Bing）＋正規表現抽出＋電話抽出＋MX篩い` だけで企業選定〜担当者マスタ出力まで通ります。`.env` に下記キーを入れた項目だけ、自動で高精度経路に切り替わります（コード変更不要）。

| 環境変数 | 入れると点火する経路 | 無いときのフォールバック |
|---|---|---|
| `GBIZ_TOKEN` | gBizINFO で 業種×地域の**構造化発掘**＋従業員数選別・代表者名/HP取得 | Bing検索ベースの発掘（`discover.js`） |
| `NTA_APP_ID` | 国税庁APIで**商号→法人番号**の名寄せ | 名寄せスキップ（法人番号空欄） |
| `GEMINI_KEY` | **ICP自動生成**＋**採用担当者AI抽出** | 手動ICP（.env）＋正規表現抽出 |
| `HUNTER_KEY`＋`DO_EMAIL_VERIFY=true` | メール実在検証 | MX篩い＋パターン推測（確度0.4） |
| `SHEET_ID`＋サービスアカウント | 「担当者マスタ」タブへ upsert 出力 | ローカルCSV（`leads.csv`）のみ |

# リスト品質スコアリング（テレアポ・アポ率の最適化）

作成した担当者マスタ（`leads.csv`）を、テレアポのアポ率を左右する**4ディメンション加重モデル**で採点し、架電優先度を振り分けます。実装は [`src/quality.js`](src/quality.js)（純ロジック）＋ CLI [`src/score-list.js`](src/score-list.js)。

```powershell
node src/score-list.js                 # leads.csv を採点 → leads.scored.csv
npm run score                          # 同上
node src/score-list.js --input leads.csv --out scored.csv --top 30
node src/score-list.js --min 70        # 「今週架電」(総合70+)だけをCSV出力
```

## スコア設計（合計100点・加重平均）
| ディメンション | 既定ウェイト | 見るデータ |
|---|---|---|
| ① ICP適合度 | **30%** | 従業員規模（スイート100〜250名）・業種一致・地域一致・設立継続性・補助金 |
| ② 採用インテント | **35%（最重要）** | 求人出稿シグナル（あれば）／無ければ採用ページ・担当者HITの**代理推定** |
| ③ データ到達性・品質 | **20%** | 電話番号の妥当性・メール確度・担当者/部署・公式URL・データ鮮度 |
| ④ タイミング（季節） | **15%** | 新卒採用スケジュール連動の月係数（前年9-12月=計画ピーク100、1-3月=85、4-6月=70、7-8月=55） |

`総合 = 0.30×ICP + 0.35×インテント + 0.20×データ + 0.15×タイミング − ネガ調整`。
ネガ調整は入力CSVに `除外フラグ`／`DNC`／`既存顧客`／`競合ATS導入` 列があれば自動減点。
ウェイト・閾値は `.env`（`QUALITY_W_*`／`QUALITY_PRIORITY_HIGH`／`QUALITY_PRIORITY_MID`）で調整可能。

## 出力と優先度
採点済みCSVは元の列に `品質スコア / 優先度 / ICP適合 / 採用インテント / データ品質 / タイミング / インテント根拠 / スコア根拠` を追記。総合スコアで降順ソートし、コンソールに各ディメンション平均・優先度内訳・上位社を表示します。
- **今週架電**（総合70+）／**ナーチャリング**（45-69）／**後回し**（<45）の3段階。

## 採用インテントを「実データ」化する（最重要ディメンション）
キー無しの現状では、採用インテント（35%）は**採用ページ有無・担当者HITの代理推定**で採点され、`インテント根拠=代理推定` と表示されます。これを実データに上げるには、入力CSVに求人出稿データの列を足すだけで自動的に本スコアへ切り替わります（HRogリスト等のCSVを社名で結合）：

`新卒出稿`（○/掲載中）・`出稿媒体数`（数値）・`予想出稿金額`（数値）・`出稿継続性`（○）・`現在求人掲載中`（○）

> 求人出稿データは購買意図を60-90日先行して示す最良の早期シグナル。MOCHICA（新卒・アルバイト）用途では、全雇用形態をカバーする HRogリスト等の連携が最も効果的です。

# 多系統ソース統合でリスト精度を上げる（収集戦略の実装）

「**新卒採用フラグ**を軸に逆算し、**件数でなく下流の接続→アポ率**でソースを評価する」という収集戦略を、3つの仕組みで実装しました。1社1レコードのスコアリング（上のセクション）の**手前**に、**複数ソースの統合・名寄せ**を、**後ろ**に**ソース別の利回り評価ループ**を足した形です。

```
[複数ソースCSV] ──merge.js──▶ [名寄せ済みマスタ] ──quality.js──▶ [採点・優先度付きリスト] ──source-kpi.js──▶ [ソース別利回り→配分最適化]
   A 採用メディア(新卒フラグ)      法人番号で重複排除          4次元＋新卒フラグ軸＋★         接続→アポ→受注 でソースを採点
   B 企業属性(gBiz等)            役割固定でフィールド採用      属性ランクA/B/C×intent★        低利回りを止め高利回りに寄せる
   C intent/トリガー             出所(取得元媒体)を刻む        系統C★≥3で優先度を割り込み
   D ネットワーク/既存資産
```

## 系統（ソースの役割）
| 系統 | 何が取れるか | 役割 | サンプル |
|---|---|---|---|
| **A** 採用メディア起点 | **新卒フラグ**＋採用規模＋痛みシグナル | 起点（最優先） | `sources/A-mynavi.csv` |
| **B** 企業属性起点 | 従業員数・業種・地域・設立・補助金・代表者名 | 母集合・名寄せ・肉付け | `sources/B-gbiz.csv` |
| **C** インテント/トリガー | プレスリリース・出稿増・採用ページ更新・辞退・来期検討 | "今動いている"で優先度を上書き | `sources/C-prtimes.csv` |
| **D** ネットワーク/既存資産 | 失注先・既存リレーション・反応者（連絡先付き） | 転換率最大の温かいリード | `sources/D-shitchu.csv` |

## ① 統合ビルド（マージ→採点→出力）
```powershell
node src/build-list.js --sources sources/manifest.json --out leads.master.csv
npm run build-list                                   # 同上（既定manifest）
node src/build-list.js --sources sources/manifest.json --kpi sources/outcomes.csv   # KPIまで一気に
node src/build-list.js --dir sources                 # manifest無し：ファイル名 A-/B-/C-/D- で系統推定
```
`sources/manifest.json` に各ソースを宣言します（`system`=系統 / `source`=KPI帰属の単位名 / `intent`=既定★ / `cost_per_company`=取得コスト）。実行すると:
- **突合キー=法人番号**（無ければ**正規化社名**：法人格・㈱・全角・記号を吸収）で**重複排除**。
- **役割固定マージ**：新卒シグナルは系統A、属性は系統B、トリガーは系統C の値を優先採用。連絡先は確度の高い方。
- 各行に **`取得元媒体`（出所の連結）/`系統`/`起点ソース`/`新卒フラグ`/`intent★`/`ソース数`** を刻む（KPI帰属とトレーサビリティの土台）。
- そのまま4次元採点し、**優先度降順のマスタCSV**と、名寄せ統計・新卒フラグ率・★分布・上位社を表示。

## ② スコアリングの強化（精度の核）
`src/quality.js` を収集戦略に合わせて拡張しました（既存挙動は後方互換）。
- **新卒フラグ軸**：`新卒フラグ` が立っていれば、出稿データが無くても**採用インテントを実シグナル**として採点（`インテント根拠=実シグナル`）。設計の背骨。
- **intent★トリガー（系統C）**：`プレスリリース`/`出稿増`/`採用ページ更新`/`インテント`/`辞退シグナル` の数＝★（0-5）。intentに最大+30点上乗せ。
- **属性ランク A/B/C**：ICP適合スコアで階級分け（A≥75 / B≥50 / C）。`属性ランク × intent★` で優先度を読む。
- **優先度の割り込み**：系統Cの強トリガー（**★≥3**）かつ属性がC級でない行は、総合スコアが中位でも**今週架電へ1段昇格**（"今動いている"を逃さない）。属性不明（C級）は割り込ませず、まず系統Bで肉付けしてから昇格させる設計。
- **ゴールデンタイム**（設計#7）：`辞退シグナル`=○ で**タイミング満点**（夏〜秋の辞退期は最も刺さる）、`来期検討`=○ で加点（秋〜冬の採用設計期）。

## ③ ソース別KPI評価ループ（設計#9「必ず回す」）
件数で満足せず、**下流（接続→アポ→商談→受注）と1社あたりコスト**でソースを採点し、低利回りを止め高利回りに寄せます。
```powershell
node src/source-kpi.js --leads leads.master.csv --outcomes sources/outcomes.csv
npm run kpi
node src/source-kpi.js --leads leads.master.csv --attr touch    # 接触した全ソースに帰属（既定は起点ソース）
node src/source-kpi.js --leads leads.master.csv                  # 成果CSV無し＝カバレッジ(件数/適合率)のみ
```
- **成果CSV**（`sources/outcomes.csv`）は `法人番号`(無ければ`企業名`) をキーに `接続/アポ/商談/受注/コスト` 列。テレアポ結果をここに書き戻して回します。
- ソース別に **適合率・接続率・接続→アポ率・商談化率・受注率・1社コスト・アポ単価/受注単価** を算出。
- 利回り（受注率、無ければアポ率）の**中央値×1.2以上＝「寄せる」／×0.6以下＝「止める検討」**を自動提示（母数<5は判定保留）。**2週間サイクル**（`KPI_CYCLE_DAYS`）で回す前提。

## 運用の型（フェーズ）
1. **濃いセルを作る**：系統A（マイナビ等の新卒フラグ）を起点に、系統B（gBiz）で属性を肉付け、系統C（PR TIMES等）で"今動いている"を割り込ませ、最濃度セル（新卒フラグ×従業員スイート×Aランク業種×痛みシグナル）を**今週架電**へ。
2. **回す**：架電結果を `outcomes.csv` に記録し `source-kpi.js` で**ソース別利回り**を2週間ごとに判定 → 配分を最適化。
3. **継続供給**：HRog出稿検知・プレスリリース・インテントを定期で系統A/Cに追加（CSVを増やしてmanifestに足すだけ）。

## 設定（`.env` / `src/config.js`）
`SYSTEM_INTENT`（系統別★）・`FIELD_OWNERS`（役割固定）・`INTENT_TRIGGER_COLS`（トリガー列）・`SHINSOTSU_FLAG_COLS`（新卒フラグ列）・`GRADE_A_MIN`/`GRADE_B_MIN`（属性ランク閾値）・`INTENT_OVERRIDE_STARS`（割り込み★）・`KPI_FIT_SCORE_MIN`/`KPI_OUTCOME_COLS`/`KPI_CYCLE_DAYS`（KPI）で調整可能。

## コンプライアンス（重要）
- ナビ/ワンキャリア/Indeed等の**スクレイピングは各社ToS/robotsに抵触し得る**ため、本ツールは**取得済み/許諾済みCSVの取り込み・統合・採点**に徹します（系統A/Cは半手動・許諾データ前提）。自動化は公開APIの系統B（gBiz/法人番号）に寄せます。
- 名簿のオプトアウト・特定電子メール法（メールはオプトイン）・個人情報の適正取得を遵守して運用してください。

# 採用担当者「個人名」取得層（Wantedly / ハローワーク）

中堅〜大手中心の母集団（このgBiz由来1000件）は、自社採用ページ・メールに採用担当の**個人名を出さない**（窓口は「採用担当」「recruit@」）。個人名が公開で出るのは**採用広報が活発な媒体**＝Wantedly等。そこを社名で引いて拾う層です。実装は [`src/scrape-names.js`](src/scrape-names.js)（アダプタ）＋ [`src/build-names.js`](src/build-names.js)（駆動）。

```powershell
npm run names                                            # leads-daihyou-1000.csv → sources/A-names.csv
node src/build-names.js --in leads-daihyou-1000.csv --out sources/A-names.csv --limit 200 --concurrency 2
node src/build-names.js --include-experimental           # ハローワーク枠も試す（要セッション較正）
```

- **取得は全て `polite.js` 経由**（robots遵守・ホスト別レート制限・7日キャッシュ）。robots禁止なら `blocked` でスキップし、ゴミを後段へ流さない。
- **氏名の確定は既存資産を再利用**：`extract.js`（採用文脈の正規表現・conf0.7）＋ `jp-names.js`（姓ガゼッティアで`isFullName`検証）＋ 媒体投稿者セレクタ（conf0.5）。**姓辞書で検証できないトークンは人名にしない**（精度優先）。
- 出力 `sources/A-names.csv`（`企業名/法人番号/採用担当者名/役職/部署/取得元媒体/根拠URL/担当者確度/探索結果/取得日`）は **manifest に系統B（肉付け）で登録済み**。`build-list.js` のマージで `採用担当者名` を**確度優先**で採用（系統A扱いにすると全社へ新卒フラグが誤って立つため、あえてB）。

| アダプタ | 状態 | 備考 |
|---|---|---|
| **Wantedly** | 較正済み（静的取得で動作） | エンドポイントは `wantedly.com/projects?q=<社名>`（SSR・robots許可）。投稿者名は `[class*="MemberName"]` から抽出。**会社一致を必須化**し無関係企業の名を出さない。`NAMES_RENDER=auto` でPlaywright描画も可（chromium同時起動はメモリを食うため並列1推奨） |
| **ハローワーク** | experimental | 公的データで低リスクだが現行ネットサービスは**JSF（ViewState付きセッション）**でGET検索が成立しにくい。担当者欄は係名止まりも多い。`--include-experimental` で枠を起動 |

> 純ロジック（`firstFullName`/`extractPersonName`/`pickDetailUrls`/`namesMatch`/`companyOnPage`）は `npm test` で回帰検証済み（ネットワーク不要）。抽出経路は実証済み（例: 「株式会社FLINTERS」→ 投稿者「早瀬峻介」を根拠URL付きで取得）。

### 実測と限界（このgBiz中堅〜大手1000件での歩留まり）
実母集団10社（JFEスチール/住友商事/日産化学/五洋建設等）で試走した結果、**個人名HIT 0%**。`探索結果`は全件 `Wantedly:company-mismatch`＝**検索は募集を返すが、対象の中堅大手はWantedlyの結果に現れない**（Wantedlyの全文検索は社名スコープでなく人気のスタートアップ募集を返す）。これは [採用担当者名が取れない真因＝母集団] の決定的な裏付けで、抽出技術ではなく**母集団の問題**であることを再確認した（会社一致ガードが誤名の混入を完全に防いでいる点も確認）。

> **使いどころ**：本層は**母集団を採用広報の活発なSME/ベンチャーに寄せたとき**に効く（個人名が募集投稿に出るため）。中堅大手中心の現リストでは収量は出ない。媒体セレクタは将来のDOM変更時に `scrape-names.js` の `NAME_ADAPTERS[].authorSel` / `detailSel` を再較正する。

## MOCHICA向けリスト（アポが取れる基準で選定）

「完成リストが今のリストよりアポを取りやすい」と**自信を持って言い切る**ために、汎用ICP採点（`quality.js`）と決別して MOCHICA 専用の **アポ取得期待値モデル** を新設した。

### 確定ターゲット
- **企業像**：新卒を増やしたい中小（従業員 **50〜150名** がスイート）
- **タイミング**：**28卒の媒体選定・採用設計期**を最優先（＝いま採用管理ツールを比較検討するテーブルに乗る瞬間）
- **到達性**：テレアポで“担当者名指し”で繋ぐため、**電話＋採用担当者名**を重視

### 採点ロジック（`src/mochica-fit.js`）
アポ取得期待値 = Σ(次元 × 重み) − ペナルティ。各次元に**確信度**を併走させ、スコアが実データ由来か代理推定由来かを可視化する。

| 次元 | 重み | 中身 |
|---|---|---|
| ① 新卒インテント | 0.34 | 実在性で階級化：**マイナビ実取得 > 新卒フラグ確定 > 求人検索で採用中 > 採用ページのみ(代理)**。複数媒体出稿・募集職種数で痛みの濃さを加点 |
| ② 規模フィット | 0.26 | 50-150名=100。**大企業(自前/競合ATS濃厚)・零細(新卒母数薄い)を強めに減点** |
| ③ 到達性 | 0.20 | 電話妥当＋採用担当者名（名指し架電可）＋部署/役職 |
| ④ タイミング | 0.14 | 28卒設計期係数（6-8月＝サマーインターン準備＋媒体選定の山）＋辞退/更新トリガーでレコード単位に引き上げ |
| ⑤ 継続・信用 | 0.06 | 設立年（毎年新卒を採れる体力）＋補助金 |

ペナルティ：競合ATS導入・大企業・既存顧客・DNC を減点。

### 実行（`npm run mochica`）
```

npm run mochica:enrich     # 上位社をマイナビ実取得して採用担当者名を補完→再採点
```

- 出力 `leads-mochica.scored.csv` は先頭に **アポ期待度／優先度／確信度／なぜ今なぜこの企業／各次元スコア／採点根拠** を付与。

# ICP適合 完全新規リスト ビルダー（ワンコマンド）

「**既存母集団（`data/leads-consolidated-all.csv`）＋納品台帳（`data/_delivered-ledger.csv`）の外にいる × ICP適合 × 採用担当者名あり**」の**呼べる名指しリスト**を、コマンド1本で生成します。実装は [`src/build-new-icp-list.js`](src/build-new-icp-list.js)。ICPハードルール [`src/icp-rules.js`](src/icp-rules.js)（リスト作成条件の単一の真実源）と重複防止台帳 [`src/delivered-ledger.js`](src/delivered-ledger.js) を内蔵し、`harvest → map → enrich → format` の4フェーズを1プロセスで通します。

```bash
npm run new-list            # 全フェーズ（マイナビ再スクレイプあり）
npm run new-list:from-raw   # 既存rawを使い map以降だけ（= --skip-harvest）
npm run new-list:help       # ヘルプ（全オプション表示）
```

> **必要環境**：harvest / enrich は Playwright chromium を使います。未導入なら `npx playwright install chromium`。

## パイプライン（4フェーズ）
| フェーズ | 中身 | 中間出力 |
|---|---|---|
| **1. harvest** | マイナビ現行卒年サイトを**勝ち筋（非IT）キーワード**で巡回。discovery段階で社名を pool/台帳と突合し、**既存社名はスクレイプせずスキップ**（時間節約）。`.seen` 併記で**再開可** | `data/recruiter-mynavi-new<gy>.csv` |
| **2. map** | `qualifiesForList`（担当者名＋電話＋新卒6名＋従業員100-2000＋非IT）で選別し、pool/台帳になし＝**完全新規**だけを consolidated スキーマへ写像。氏名のスクレイプ断片除去も実施 | `data/leads-new-mynavi-mapped.csv` |
| **3. enrich** | 会社概要（outline.html）を追加取得して**都道府県／設立／従業員**を補完。**IT名／規模超(>2000)／非人名**を除外（`--skip-enrich` で省略可） | 同上を上書き |
| **4. format** | [`src/format-bales.js`](src/format-bales.js) で **BALESCLOUD 取込構造（266列）** へ整形し、**納品台帳へ記録** | **最終成果物** |

## ICP適合の絶対条件（`src/icp-rules.js` 準拠）
- **採用担当者名あり**・**電話番号あり**・**年間新卒6名以上**・**従業員100〜2,000名**・**非IT/ソフトウェア**（IT は経路・規模を問わず成約率6%前後で構造的除外）。
- IT絶対除外は **map・enrich の両方**で効かせているため、`--skip-enrich` でもIT名企業は落ちます。
- 代表者名の担当欄流用（役職が代表/社長/取締役系）は除外。規模帯に応じた提案プラン（`proposalTier`）も自動付与。

## 収量の勘所（重要）
- **ボトルネックは企業数でなく「採用担当者名」**。名指しリストは必ず**現行で最も成熟した卒年サイト**（既定 gy=27）で回すこと。季節初期の卒年サイトは規模適合でも担当者名が伝言板に未掲出で歩留まりが落ちます。
- 既存の callable プールは出し切り済みのため、**新規の実収量は harvest のキーワード数に依存**します。増やすときは `--keywords` で勝ち筋業種をさらに細分してください。
- 完全新規が **0件**なら「母集団拡張（キーワード増／卒年切替）」または「条件緩和」が必要、というメッセージで正常終了します（バグではありません）。
- 出力は 266列の BALESCLOUD 取込構造。**納品時はダウンロードフォルダへ移動**して扱ってください。個人情報を含むため取り扱いは [SECURITY.md](SECURITY.md) に従います（`data/**` は既定 `.gitignore` 済み）。

# 新卒「母集団課題」ニーズ特化リスト（BALES再アプローチ層）

BALESCLOUD の既存リード **22,892件**（過去架電・商談ヒアリング履歴つき）から、**「新卒の母集団形成に課題がある」と自ら語ったリードだけ**を抜き出し、そのまま **BALESCLOUD取込構造（266列）** で再アプローチ用リストにするビルダーです。規則エンジンは [`src/boshudan-needs.js`](src/boshudan-needs.js)（純ロジック・単一の真実の源）、ドライバは [`src/build-boshudan-list.js`](src/build-boshudan-list.js)。

```bash
npm run boshudan            # 判定→除外→名寄せ→採点→2ファイル出力
npm run boshudan:strong     # 強シグナル（母集団を課題と明言）だけに絞る
npm run test:boshudan       # 判定規則の単体テスト（実データ由来の19ケース）
node src/build-boshudan-list.js --min-score 90 --limit 200   # 上澄みだけ切り出す
```

## なぜ「BALES既存リード」なのか
「母集団が集まらない」という**生の声は自由記述履歴にしか無く、それを持つのはBALESだけ**（SFのMOCHICA参照エクスポートは自由記述列を持たない。cf. 検討時期の抽出と同じ理由）。つまり**ニーズを実データで裏取りできる唯一の母集団**であり、`npm run new-list`（完全新規の名指しリスト）とは層が違う**温かい再アプローチ層**です。

## 判定の骨格（誤爆させないための4層）
| 層 | 役割 | 例 |
|---|---|---|
| **ニーズ規則（強）** | 母集団（形成）そのものを課題・悩み・不足と明言／ヒアリング課題欄に母集団形成が挙がる | 「歩留りよりも母集団の方が課題。応募が来ない」「感じている課題 ・歩留まり改善／**母集団形成**」 |
| **ニーズ規則（中）** | 母集団が薄い実態の言及 | 「ナビに費用かけているのに応募が少ない」「理系の学生が集まらない」 |
| **充足規則** | 「足りている/困っていない/安定」＝ニーズ**なし**として打ち消す | 「母集団も歩留まりも課題感もなく順調」「プレエントリー2000名」 |
| **中立・帰属ガード** | 事実記入・未編集テンプレ・中途の痛み・自社プロダクト説明を除外 | 「母集団形成**方法**：マイナビ」「選択肢が7つ丸残り」「中途は苦戦」「MOCHICAも母集団強化した」 |

> **最大の誤爆源はヒアリング様式**でした。`■採用チームとして感じている課題 ・歩留まり改善／工数削減／…／母集団形成／その他` は**選択肢テンプレの丸残り**（＝何も選ばれていない）で、実データ上213件。7項目中6つ以上残っていれば未編集とみなして数えません。

## 除外（架電不能・アプローチ不可・ICP不適合）
アプローチ禁止／架電拒否・新規営業一律お断り（`talk-analysis.js` の断り理由分類を再利用）／新卒やってない・担当外／採用1~2名／失注理由=接触人数不足／電話番号なし／**商談進行中・受注済み**／MOCHICA既存顧客（`company-match.js`）／IT・ソフトウェア（`icp-rules.js` の絶対除外）／従業員100名未満（**判明している場合のみ**）。

- **失注済みのコンバートは残します**（＝失注リサイクル。深く商談した相手で母集団課題が記録に残っている＝最も温かい）。失注日が無いコンバートだけが「進行中/受注済み」として落ちます。
- 同一社の複数リードは **強度→スコア→新しさ** で1社1行に名寄せ（`company-match.js`）。

## 採点（0-100・透明な加点式）
`ニーズ強度（強45/中30）＋名指し可10＋新卒6名以上15＋従業員スイート14＋他社ATSなし8＋再架電可ステージ7＋検討開始が直近8＋過去商談あり5`。
**A：今週架電（90+）／B：次点（78-89）／C：ナーチャリング（〜77）**。加点根拠は1社ごとに `スコア根拠` 列へ出力します。

## 出力（2ファイル）
| ファイル | 用途 |
|---|---|
| `data/leads-bales-boshudan.csv` | **BALESCLOUD取込用（266列・原本の値そのまま／Noだけ振り直し）**。リードID・リードURLも保持するので既存リードにそのまま戻れる |
| `data/bales-母集団課題-根拠.csv` | 架電者が読むレビュー用。**優先度／スコア／ニーズ強度／ニーズ分類／根拠（実際の記録の抜粋）／名指し可否／接点区分／失注理由**などを1行に |

> 取込用CSVは**原本を書き換えません**（顧客の課題感などのCRM値を上書きしない）。根拠は必ずレビュー用CSV側で確認してください。個人情報を含むため取り扱いは [SECURITY.md](SECURITY.md) に従い、**納品時はダウンロードフォルダへ移動**します。

# 利用ATS判定（エントリーページURL → 採用管理システム）

エントリーページのURLから、その企業が使っている **ATS（採用管理システム）** を判定します。判定ロジックは [`src/ats.js`](src/ats.js)（純ロジック・ネットワーク不要）、CLIは [`src/enrich-ats.js`](src/enrich-ats.js)。詳細は [docs/ats-detection.md](docs/ats-detection.md)。

```bash
npm run ats -- --url "https://www.career-cloud.asia/27/form/entry?id=16849397703997"
# → ATS: 採用一括かんりくん / ベンダー: HRクラウド / 営業メモ: 競合ATS導入済み＝リプレイス提案

npm run ats -- --in data/leads.csv --out data/leads-ats.csv        # 一括（URLのみで判定）
npm run ats:live -- --in data/leads.csv --out data/leads-ats.csv   # 決まらない行だけページ取得（robots遵守）
npm run ats:all                                                     # 全社スイープ（公式サイト→採用ページ→エントリー導線）
npm run ats:lists                                                   # 利用中ATS別のリストを一括生成
npm run test:ats                                                    # 単体テスト（test:all にも組込済み）
npm run ats:verify                                                  # 目視35社で精度を測る（誤出荷が出たら失敗）
npm run ats:shinsotsu                                               # 27卒/28卒のATS利用企業 横断一覧
```

| URLのホスト | 判定 |
|---|---|
| `career-cloud.asia` | 採用一括かんりくん（管理くん・HRクラウド） |
| `job.axol.jp` / `mail.axol.jp` | アクセスオンライン AOL/AOLC（マイナビ） |
| `hrmos.co` | HRMOS採用（ハーモス・ビズリーチ） |
| `sonar-ats.jp` / `i-web.jp` / `jobsuite.jp` / `ats.jobcan.jp` ほか | 各競合ATS |
| `job.rikunabi.com` / `job.mynavi.jp` ほか | ナビ媒体（ATSではない＝未導入の可能性） |
| Googleフォーム / formrun / Contact Form 7 | 汎用フォーム＝**ATS未導入シグナル** |
| `mochica.jp` | MOCHICA（自社）＝既存顧客として除外 |

ベンダーの検出は **①URLホスト（0.95）→ ②リダイレクト後URL（0.90）→ ③HTML内の埋め込み iframe/script/form action（0.85）→ ④本文マーカー（0.60）** の順。自社サイトにフォームを埋め込む構成はURLに出ないため③が要です。サブドメインは一致扱い、部分文字列一致は誤検知になるため弾きます（`career-cloud.asia.evil.com` は不一致）。

## 新卒で使っているATSだけを採る（2026-09 改訂）

**ベンダーを検出しただけでは採用しません。** 35社を目視監査したところ、旧ロジックの適合率は **45.7%（19社が誤り）** でした。誤りの内訳はほぼ4パターンです。

| # | 誤りのパターン | 実例 |
|---|---|---|
| A | **中途採用のATSを掴んでいた**（約6割） | 新卒はマイナビ／i-web、中途だけHRMOS |
| B | 新卒採用をしていない会社に印を付けた | 中途しか募集していない |
| C | 本文に製品名の**文字列**が出ただけで確定（確度0.60） | HR系企業が記事内で製品名に言及 |
| D | **ベンダーの製品紹介ページ**へのリンクを導入済みと読んだ | `hrmos.co/ats/` は製品ページ |

MOCHICAは新卒ATSなので、中途のHRMOSを掴んで「リプレイス提案」と出すと架電が空振りします。そこで判定単位を「企業 → ATS」から **「企業 × 用途（新卒/中途） → ATS」** に変え、採否ゲート（[src/ats-scope.js](src/ats-scope.js)）を1か所に集約しました。

**確定を出すのは次の2経路だけです。**

1. **ATSページ本文に新卒の募集がある** — `新卒採用`／`卒業見込`／`27卒`／`2027年3月卒業` など単独で決め手になる語。求人一覧は新卒と中途が混ざるので多数決にせず、決め手が1つでもあれば採ります。
2. **ATSのURL自体に新卒の印がある** — `career-cloud.asia/**27**/form/entry`、`.../risu_group**2027**/` のような卒年。

逆に、**参照元ページ側の文脈では確定しません**（「新卒採用｜中途採用」が並ぶナビの中のリンクで誤確定するため）。その他の安全弁：

- `第二新卒歓迎` は中途求人の常套句なので、**新卒として数えない**（部分一致で「新卒」に化けるのを防ぐ）
- 顧客テナントのURL（`hrmos.co/pages/<企業ID>/`、`<企業>.sonar-ats.jp`）でなければ証拠にしない → D を排除
- 実URLの無い本文マーカーは**必ず要確認**に落とす → C を排除
- `導入事例`／`比較`／`コラム` の文脈は除外

結果（同じ35社・[src/ats-eval.js](src/ats-eval.js) で計測）:

| | 旧ロジック | 改訂後 |
|---|---|---|
| 確定として出力 | 35社 | 11社 |
| **誤出荷** | **19社** | **0社** |
| 適合率 | 45.7% | **100%** |
| 再現率 | 100%（誤りを含む） | 68.8% |

確定にできなかった分は `data/ats-scan/ats-scan-要確認.csv` に理由つきで残るので目視に回せます。**取りこぼしてもよいが、誤って載せない**という方針です。

```bash
npm run ats:verify        # 目視35社を再スキャンして精度を測る（誤出荷>0なら終了コード1）
npm run ats:eval          # 既存のスキャン結果を採点
npm run ats:eval:legacy   # 改訂前の数字（45.7%）
npm run test:ats-scope    # ゲートの単体テスト
```

## 全企業スイープ（`npm run ats:all`）

エントリーURLが分かっていない企業も含め、手元の**全社**（統合マスタ＋ターゲット＋BALESをホストで名寄せして実測11,232社）を公式サイトから辿って判定します（[src/enrich-ats-all.js](src/enrich-ats-all.js)）。1社あたり **最大4取得**（`--max-fetch`）で、①URLに新卒の印があれば取得せず確定 ②起点ページのATS参照を**実URL＋周辺文脈つき**で収集 ③「新卒」を含むリンクを最優先に採用ページへ1hop ④ATSページ自体を取得して新卒か中途かを本文で確かめる。④が改訂の肝で、中途の入口（`/mid/`・中途カテゴリ）に着地した場合は同じベンダーの別URLをもう1つだけ試します。

出力は3本に分かれます。

| ファイル | 中身 |
|---|---|
| `ats-scan-確定.csv` | **新卒での利用を確認済み。リスト生成に使うのはこれ** |
| `ats-scan-要確認.csv` | 証拠不十分。目視の作業リスト |
| `ats-scan-all.csv` | 全件（`判定グレード` `新卒根拠` `用途` `ATS URL` `中途ATS` `候補ATS` 列つき） |

`判定グレード` は `確定`／`中途用`／`要確認`／`新卒採用なし`／`該当なし`。**ATS列が埋まるのは確定の行だけ**で、これが誤出荷を止める唯一の場所です。

1社1行の追記専用ジャーナル（`data/ats-scan/journal.jsonl`）に逐次書くので、**途中で止めても成果は残り、再実行で続きから走ります**（`npm run ats:all:rebuild` で取得せずCSVだけ再生成）。旧ロジック（`スキーマ<2`）で書かれた行は読み込み時に**「要確認」へ降格して再スキャン対象に戻す**ので、誤判定のまま出荷されることはありません。出力の `CRMとの一致` 列でCRMの手入力値との食い違いを監査できます。

## 卒年別「新卒でATSを使っている企業」横断一覧（`npm run ats:shinsotsu`）

スキャン結果の**確定行だけ**を取り、卒年（27卒／28卒）で束ねたツール横断の一覧を作ります（[src/build-ats-shinsotsu-list.js](src/build-ats-shinsotsu-list.js)）。競合ATSごとにトークが変わるうえ、卒年で切替検討のタイミングが変わるので **ATS×卒年の2軸**で並べられる形にしています。

卒年は証拠から取ります。①ATSのURLの卒年（`career-cloud.asia/**27**/form/entry`、`..._group**2028**/`）②ATSページ／採用ページ本文の `27卒`・`2027年3月卒業見込み`。**確定した行にしか卒年を付けません**（中途・要確認の行に卒年が付くと一覧の意味が壊れるため）。

```bash
npm run ats:shinsotsu                                    # 27卒・28卒
node src/build-ats-shinsotsu-list.js --years 27,28,29
node src/build-ats-shinsotsu-list.js --include-unknown-year
```

出力（`data/ats-shinsotsu/`）:

| ファイル | 中身 |
|---|---|
| `現行新卒-ATS利用企業-横断一覧.csv` | **実用版。** 27/28卒の証拠がある行＋「新卒採用は確認できたが卒年の記載がない」行 |
| `現行新卒-ATS利用企業-架電可.csv` | 上のうち架電できる分だけ（アプローチ禁止・架電拒否・電話なしを除く） |
| `27-28卒-ATS利用企業-横断一覧.csv` | 厳密版。卒年の証拠がある行だけ |
| `ツール別/<ATS名>-27-28卒.csv` | 競合ごとに束ねたもの |
| `対象外卒年-新卒ATS確定.csv` | 25/26卒しか見えなかった行（過年度ページ＝除外分の確認用） |
| `_ATS別サマリ.csv` | ATS×卒年の社数 |

**なぜ実用版と厳密版を分けるか**: 2026-09時点で動いている新卒採用は27卒（選考終盤）か28卒（立ち上がり）しかありません。サイトに卒年を書かず「新卒採用」とだけ書く企業も多いので、卒年が読めないだけで落とすと架電先を大量に失います。両方出して `卒年` 列で区別できるようにしています。

連絡先はBALES（架電履歴＝架電可否の根拠を持つ）を優先し、空欄を統合マスタで補完します。BALES未登録でも電話があれば `架電可（BALES未登録＝新規）` として残します。

> CRMの `カスタム情報：利用中ATS`（架電で聞き取った実測1,747社）を軸にしたリストは `npm run ats:lists` の方です。こちらはURL実測なので**卒年が付く**代わりに社数が絞られます。用途で使い分けてください。

## 管理ツール別リスト（`npm run ats:lists`）

BALES既存リードを**使っている管理ツールごとに切り分けて**リスト化します（[src/build-ats-lists.js](src/build-ats-lists.js)）。CRMの `カスタム情報：利用中ATS` は手入力で `sonarATS`／`SONAR`、`採用一括かんりくん`／`管理くん` と表記が割れているため、`normalizeAtsName()` で名寄せしてから束ねます。`--enrich` にエントリーURL判定の結果を渡すと、CRMが空の行だけを補完します（**実測値は上書きしない**）。

除外・名寄せ・採点の基準は母集団課題リストと同じ（アプローチ禁止／架電拒否／電話なし／商談進行中／MOCHICA既存顧客／IT業種／従業員100名未満）。出力は `data/ats-lists/` にツールごとの **取込用CSV（BALES原本列）** と **根拠つきレビューCSV**、加えて `_全ツール横断-根拠.csv` と `_ATS別サマリ.csv`。

`--enrich` に渡すCSVに `判定グレード` 列があれば **`確定` の行だけを採用**します（中途利用・証拠不十分は合流させない）。

出力列は `ATS` `ATSベンダー` `ATS種別` `ATS確度` `ATS根拠` `判定グレード` `新卒根拠` `用途` `ATS URL` `候補ATS` `ATS併用` `営業メモ` `ATS判定日`。手入力で空が多い `カスタム情報：利用中ATS` を埋めたい場合は `--fill-col "カスタム情報：利用中ATS"`（**空セルのみ補完・既存値は上書きしない**）。ベンダー追加はコードを触らず `data/ats-registry.json` で可能です。

# 採用シグナル → ホットリード（「誰に架けるか」を毎日組み替える）

企業リストを上から架電する方式は、**架電先が固定**で母集団が枯れる（callable/ICPプールは実測で枯渇済み）。
このモジュールは軸を「業界」から「**出来事**」に移す。

> 建設会社だから架電する → ✗
> **今月、求人が3件→12件に増えた**建設会社だから架電する → ○

```bash
npm run hot:collect     # ① 採用シグナルの素材を収集（PR TIMES・無料・robots遵守）
npm run hot:ingest -- <求人CSV> --source mynavi   # ② 日次スナップショットを台帳へ（差分の元）
npm run hot             # ③ 採点・除外突合 → 今日のホットリストCSV
npm run hot:daily       # ①+③ を直近30日で回して台帳へ記録（cron向け）
npm run hot:s           # S/Aランクだけ
npm run hot:store       # 台帳の状態（何日分・長期掲載何社）
npm run test:hot        # 単体テスト（test:all にも組込済み）
```

## シグナルは2系統ある（設計の核）

| 系統 | 何から出るか | 例 | 実装 |
|---|---|---|---|
| **テキストシグナル** | リリース／ニュース1本 | 新工場OPEN・M&A・資金調達・採用強化・外国人採用 | `detectSignals()` |
| **差分シグナル** | 前回スナップショットとの比較 | 求人 3→12 の急増・120日超の長期掲載・新規掲載開始 | `detectDeltaSignals()` |

**「求人急増」と「採用できていない（長期掲載）」は、その日のページを見ても絶対に分からない。**
前回いつ・何件だったかを自分で覚えている必要がある。それが [src/signal-store.js](src/signal-store.js)（`data/hot-signals/state.json`）。
差分シグナルは**2回以上の観測**があって初めて出るので、日次で `hot:ingest` を回すこと（初回は基準日を作るだけで0件が正しい）。

取り込めるCSVは列名で自動判別する（`企業名` / `求人数`(=`募集職種数`) / `採用人数` / `従業員数` / `電話番号` / `担当者名` / `業種` / `都道府県`）。
つまり **マイナビ合説CSV（`data/mynavi-events/*.csv`）も `npm run mynavi:1000` の出力もそのまま食える**。

```bash
# 日次: 求人数つきスナップショットを貯める（これが「求人急増」の唯一の元）
npm run mynavi:1000                                            # 募集職種数=求人数を含む
npm run hot:ingest -- data/recruiter-mynavi-1000.csv --source mynavi
npm run hot:store                                              # 何日分たまったか
```

> `募集職種数` は `scrape-mynavi` が以前から取っていたのに出力に載っておらず、求人数の時系列が作れなかった。
> `build-mynavi-1000.js` の出力列に追加済み（既存列の後ろに追加なので取込側の互換は保たれる）。

## 熱度（heat）と配点

| 熱度 | 意味 | シグナル |
|---|---|---|
| 🔥×5 | 採用枠が今まさに増えた | 大量求人開始 / 新店舗OPEN / 新工場OPEN / 新拠点開設 / 求人急増 |
| 🔥×4 | 採用ニーズが発生する構造変化 | M&A・事業承継 / 資金調達 / 採用担当者募集 / 外国人採用開始 / 求人長期掲載 / 新規掲載開始 / 採用人数増 |
| 🔥×3 | 採用に投資する意思 | 採用サイト刷新 / ATS導入・採用DX / 求人増加 |
| 🔥×2 | 採用活動はあるが緊急性が弱い | 採用広報開始 / インターン募集 / 事業拡大 |
| 🔥×1 | 通常の採用活動 | 内定式・入社式・説明会 |

`HOTスコア = Σ(熱度点 × 鮮度係数 × 逓減係数) + ICP適合 + 架電可能性`（0-100）

- **鮮度係数** … 14日以内=1.0 / 30日=0.9 / 60日=0.7 / 90日=0.5 / 180日=0.3 / それ以降=0.15。**「今」でなければホットではない**。
- **逓減係数** … 2本目以降は 0.6→0.4→0.25…。語を並べただけの企業を満点にしない。
- **ICP適合** … 従業員300-500名 +8 / 100-2000名 +4 / 100名未満 -8、新卒6名以上 +8、**IT・ソフトは -15**（実測成約率が全業種最下位＝ホットでも売れない。cf. [src/icp-rules.js](src/icp-rules.js)）。
- **架電可能性** … 電話番号 +5 / 採用担当者名 +5（代表者名のみなら +3）。
- **規模の代理指標** … 従業員数が取れない経路（PR TIMES等）では規模フロアが一切効かず零細企業が上位に来るため、`合同会社`/`有限会社` は -10。**従業員数が判明していれば実測値を優先**し、この代理指標は使わない。

ランクは **S=80+（今日架ける）/ A=65+（今週中）/ B=50+（保持）/ C（待機）**。

## 誤爆させない3層（実データで踏んだ罠つき）

規則ベースの検出は放っておくと精度が出ない。実測（PR TIMES 28本判定）で潰した誤爆源:

| 罠 | 実例 | 対策 |
|---|---|---|
| 記事タイトルの誤爆 | 「新卒採用を強化する方法とは｜徹底解説」 | `GUIDE` ガードで解説/ランキング/調査を落とす |
| 他社事例の紹介 | 「【導入事例】A社の採用管理システム活用」 | `NEG` ガード（主語が自社でない） |
| ページ末尾タグ欄の誤爆 | 新商品リリースが**タグ「新工場」だけ**で新工場OPEN判定 | `trimBoilerplate()` で関連リンク／会社概要／タグ欄を切ってから判定 |
| 海外拠点 | 「タイのアルミ新工場が竣工」「グアテマラ新工場」 | 拠点系のみ海外ガード（国内地名が同居すれば残す） |
| 自治体の発信 | **社名「横須賀市」**は社名パターンに掛からない | 業種欄「官公庁・地方自治体」も別々に判定 |
| 同一事象の二重計上 | 「新工場を建設、生産拠点を新設」で新工場OPEN＋新拠点開設 | `subsumedBy` で具体形が上位概念を吸収 |
| 採用人数のレンジ表記 | 「11～15名」を数字連結して **1115名** | `toHire()` が下限を採り、複数コースは合計（「31～35名 / 16～20名」→47） |
| 規模不明の零細企業が上位に | 首位が**個室ピラティススタジオの合同会社** | 従業員数が不明なときだけ法人格を規模の代理指標にする（S→Aへ後退） |

## 出力（`data/leads-hotlead-YYYYMMDD.csv`）

営業がそのまま架けられる形にする。「求人を出してますよね？」ではなく**採用課題営業**の入り方を自動生成する。

| 列 | 内容 |
|---|---|
| `ランク` `HOTスコア` | S/A/B/C と 0-100 |
| `なぜ今なのか` | 🔥つきの根拠（シグナル名・何日前・根拠文） |
| `推定課題` | 「応募母数不足（枠が急に増えた）」など、最初に当てにいく仮説 |
| `今日の切り出し` | 個社別トーク。例（長期掲載）: 「◯◯様、120日間掲載が続いており**長期間ご募集されているようでしたので、母集団形成よりもその後の歩留まりの方に課題があるのでは**と思いお電話しました」 |
| `検出シグナル` `最新シグナル` `シグナル発生` | 検出内訳と鮮度 |
| `企業名` `電話番号` `担当者名` `架電宛名` `採用人数` `従業員数` `業種` `都道府県` | 架電に必要な実務列 |
| `提案セグメント` `スコア根拠` `根拠URL` `既存被り` | 提案の当て先・監査用 |

## 重複防止（ここを外すと8〜9割が既存企業になる）

除外は [src/exclusion-index.js](src/exclusion-index.js) に一本化済み（MOCHICA既存顧客 / BALES既存CRM / SF全リード / 納品済み台帳）。
**既定は完全新規のみ**。既存CRMへの再アプローチとして使いたい場合は `--include-existing`（`既存被り`列に一致マスタが出る）。
`--record` を付けると納品台帳へ記録し、翌日以降は同じ企業を出さない（cf. [src/delivered-ledger.js](src/delivered-ledger.js)）。

## 主なオプション

```bash
node src/build-hotlead-list.js --limit 100 --min-score 65   # 上位100社・A以上
node src/build-hotlead-list.js --rank S,A --record          # ランク指定＋台帳記録
node src/build-hotlead-list.js --include-existing           # 既存CRM企業も残す
node src/build-hotlead-list.js --long-days 120              # 長期掲載の閾値を120日に
node src/harvest-signals.js --signals 新店舗OPEN,資金調達 --days 30
node src/harvest-signals.js --recollect                     # URLキューを捨てて巡回し直す
```

シグナル収集はトピック巡回に10分以上かかるため、収集したURLは `data/hot-signals/url-queue.json` に12時間キャッシュする（`--queue-hours` で変更）。本文判定は1本ごとに追記するので**途中で止めても成果は残り、再実行は続きから**走る。
