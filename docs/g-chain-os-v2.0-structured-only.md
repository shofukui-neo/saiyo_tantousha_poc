# 0. なぜ再設計するか

## 0.1 v1.5 の前提破綻

v1.5は「全架電を①事実②診断③改善行動④実験⑤ナレッジに変換」する構想だったが、**②③④の中核が全てMiiTel文字起こしに依存**していた。MiiTelが供給されない運用では：

- E3〜E6（意味応答・情報獲得・課題表明・打診）＝**UNKNOWN**（Wave 0でE4 UNKNOWN率37.4%）
- LCS心理診断・Q採点・GOOD/MORE/次NGコーチング＝**発火せず**
- 実験#001（質問先行vsGIVE先行）＝**忠実度検知不能で実行不可**
- 二枠サンプリング＝**metric_coverage=0で無意味**

「会話でどう話したか」は原理的に観測できない。**この事実を受け入れ、観測できるものだけで最大の価値を出す設計に倒す。**

## 0.2 何が観測できるか（構造化シグナルの棚卸し）

Wave 0 実データで実在を確認した構造化列：

| 領域 | 実在する構造化シグナル | 何が分かるか |
|---|---|---|
| 接続 | コール結果（接続状況・接続先・結果） | E0発信→E1人接触→E2担当接続の**完全なファネル** |
| 成果 | 担当者接触：アポ獲得／商談作成日時・金額 | **アポ率・商談化率**（Wave0: アポ830・商談化805） |
| 次接点 | 次のアクション1〜16（名・予定日時・完了日時） | E7次接点・E8実施・**フォロー規律**（予定vs完了・overdue） |
| ヒアリング | 顧客の現状・顧客の課題感・エントリー数 | rep入力の**構造化ヒアリング**（transcript代替・低忠実度だが実在） |
| 失注 | 失注理由大/中/小/詳細・バッティング競合・ペンディング理由 | **失注インテリジェンス**（時期相違816・ニーズなし677・競合負け…） |
| タイミング | 検討開始時期・現利用サービス更新予定月・失注後次回アクション日 | **再活性化タイミング** |
| 属性 | 採用人数・業種・従業員規模・利用中ATS・都道府県 | **ICP適合・セグメント特徴** |
| 流入 | リードソース50種＋流入日時・タグ多数 | **ソース利回り・チャネル温度** |
| 帰属 | リード所有者・最終リードステージ | 所有者別・ステージ遷移 |
| 除外 | アプローチ禁止の種類・既存顧客突合・番号不備 | **リスト衛生** |

**結論：会話の中身以外は、ほぼ全部見えている。** 会話質コーチングを捨てても、接続・成果・失注・タイミング・リスト品質の PDCA は完全に回せる。

## 0.3 設計原則（v2.0・改定）

1. **観測できる事実だけを扱う**。会話の中身は扱わない（UNKNOWNとして黙殺せず、そもそも指標にしない）
2. 人手は同期コピペ1日1回まで。API依存ゼロ（v1.5継承）
3. **rep入力の構造化フィールド（課題感・現状）は「低忠実度の事実」**として扱う。transcript由来と混同しない（source_type＝bales_note、canonical優先度は最下位）
4. **成果ラベルは構造化で確定**（アポ／商談／失注理由）。教師データは今すぐ蓄積可能
5. コーチング（育成PDCA）を**「話し方」から「誰に・いつ・何で当てるか（リスト・タイミング・シーケンス）」へ再定義**
6. 全診断に反証可能性（根拠列＋サンプル数＋分母規則）。ブラックボックスML禁止・解釈可能なリフト分析を優先
7. KPI・実験の分母規律はv1.5継承（UNKNOWN/NOT_ELIGIBLEは分母外）
8. 人が学べる形式＝AIが学べる形式（未来情報を特徴に混ぜない・v1.5継承）
9. リスト作成システムへの**フィードバック経路を正式I/Fとして持つ**（成果→スコア更新）
10. 複雑化はスキーマに、運用は日次10分に留める（v1.5継承）

# 1. 三位一体の再定義

| 目的 | v1.5（transcript前提） | **v2.0（構造化のみ）** | 中核データ |
|---|---|---|---|
| ① 実務PDCA | E率・LCS・打診・回収 | **接続PDCA**：セグメント/ソース/時間帯/リスト別の接続率・アポ率・商談化率で週次ボトルネック1つ特定 | 接続ファネル・成果ラベル |

# 2. イベントモデル v2.0（構造化確定・会話質を除去）

## 2.1 生き残るイベント（E0-E2・E7-E8）

v1.5の4状態モデル（TRUE/FALSE/UNKNOWN/NOT_ELIGIBLE）と判定エンジンを**そのまま継承**。ただし源は構造化のみ（source_type＝bales_structured／sf／calendar）。

| E | v2.0での判定源 | observability |
|---|---|---|
| E0 発信成立 | コール結果 接続状況＝着電系（番号不備/現在使われていない＝FALSE） | 構造化＝常に観測可能 |
| E1 人接触 | 結果∈{担当者不在・受付ブロック・担当者接触:*・ヒアリング*・問い合わせ}（鳴りっぱなし＝FALSE） | 構造化 |
| E2 担当接続 | 結果∈{担当者接触:*・ヒアリング成功/不可}／接続先＝担当者 | 構造化 |
| E7 次接点 | アポ獲得→meeting_confirmed／次アクション予定日時（agreed系のみ） | 構造化 |
| E8 実施 | 商談作成日時（強）／次アクション完了日時（弱・要注記） | 構造化（時間解決はv1.5継承） |

**FALSE付与が構造化で正当**：コール結果は「観測可能だったのに担当に繋がらなかった」を明示するので、E1/E2のFALSEは信頼できる（v1.5では transcript FULL 必須だった制約が、構造化イベントには不要＝event-engine の STRUCTURED_EVENTS ルールで既に実装済）。

## 2.2 廃止するイベント／概念

| 廃止 | 理由 | 代替 |
|---|---|---|
| E3 意味応答 | 発話の意味は transcript でしか判定不能 | 廃止（指標にしない） |
| E6 打診form（two_options/vague等） | 打診の言い回しは transcript 依存 | E7の有無（打診が成立したか）で代替 |
| G層 心理仮説（G0-G4） | 冒頭切電=PKM等は発話観測が前提 | 廃止 |
| WEAK_CLOSE・PREMATURE_QUESTION | 評価的忠実度イベント＝transcript依存 | 廃止 |
| Q26採点・R6・GOOD/MORE/次NG | 実行品質は発話観測が前提 | **行動規律指標**（§6.4）へ置換 |

## 2.3 半構造化イベント（E4/E5＝rep入力・低忠実度）

E4情報獲得・E5課題表明は、**rep が BALES に入力した 顧客の現状／顧客の課題感** から `source_type=bales_note` で付与する。

- **transcript由来と厳格に区別**：canonical優先度は最下位、label_confidence≤0.5、`novelty_precision=NOTE_LEVEL`
- FALSE を付けない（メモ空欄＝「聞かなかった」とは限らない → UNKNOWNのまま）
- 正式KPIの分母には入れない（`official_metric_eligible` は常に false＝会話KPIは存在しない）
- 用途は**セグメント特徴**（課題感が入っている＝深い接触ができたリードのフラグ）としてのみ

# 4. 分析層（v2.0の5本柱）

## 4.1 接続最適化（Connection Optimization）

E0→E1→E2ファネルをセグメント軸で分解し、接続ボトルネックを特定。

- 軸：時間帯 × 曜日 × 採用人数 × 業種 × リードソース × 所有者
- 指標：E2率（担当接続/架電）・受付ブロック率・担当者不在率
- 出力：接続率上位/下位セグメント → 架電時間帯・リスト構成の是正提案

## 4.2 成果スコアリング（Outcome Scoring・§5と連動）

特徴×成果ラベルのリフト分析で「アポが出るセグメント」を定量化し、未架電リードと将来リストをスコアリング。

- 手法：解釈可能なリフト（特徴値ごとのアポ率/商談化率＋サンプル数＋信頼区間）。ブラックボックスML不使用（原則6）
- 出力：`outcome_score`（アポ期待値）→ リスト作成システムへフィードバック（原則9）
- ラプラス平滑化でn過少セグメントの過大評価を抑制

## 4.3 失注インテリジェンス（Loss Intelligence）

失注理由大/中/小を **L/C/S風の構造化帰属** に写像し、改善アクションを出す。

| 失注理由（構造化コード） | 帰属 | 改善アクション |
|---|---|---|
| 検討時期相違 | L-actionable（時期） | 検討開始時期でリスト再スケジュール |
| ニーズなし | L-actionable（ICP） | ICP適合の見直し（採用人数/業種） |
| 予算なし（来期以降も不可） | L-exogenous | 除外・長期再活性化キューへ |
| 競合負け・バッティング | C（訴求） | 競合別の訴求根拠を10_訴求マスタへ |
| 機能面 | Product | プロダクトへフィードバック |
| リスケ/情報収集 | Pending | 再活性化タイミング（§4.4） |

transcript無しでも、**失注理由コードは「なぜ負けたか」の構造化事実**。心理診断の代わりにこれを使う。

## 4.3.1 帰属の限界（正直な明示）
構造化コードは「時期・ニーズ・予算・競合」までしか分解できない。**「同じ時期相違でも、切り返せたはずか（C/S）」は判定不能**。v1.5のL/C/S副因分離はできない。これは仕様上の限界として受容する。

## 4.4 再活性化タイミング（Reactivation Timing）

リサイクル/ペンディングリード（Wave0: リサイクル8,993）を、構造化タイミング信号で再架電優先度付け。

- 信号：検討開始時期・現利用サービス更新予定月・失注後次回アクション日・失注日からの経過
- 出力：`reactivation_priority` と「今月架電すべき再活性化リード」リスト

## 4.5 行動規律（Activity Discipline・育成PDCAの実体）

次のアクション（予定日時 vs 完了日時）から、**話し方でなく行動の規律**を測る。

| 指標 | 定義 | 分母 |
|---|---|---|
| フォロー実行率 | 完了/予定 | 予定ありの次アクション |
| overdue率 | 予定超過・未完了 | 同上 |
| シーケンス完了率 | 想定ステップまで到達 | 開始したジャーニー |
| 平均フォロー間隔 | 予定→完了の日数 | 完了分 |
| 接触あたりアポ | アポ/E2 | E2成立 |

単独運用なら自分の規律、複数所有者なら所有者別。**これがコーチングの代替**（「あなたは折り返し予定の30%が期限超過。ここを詰めればアポが増える」）。

# 10. ロードマップ
