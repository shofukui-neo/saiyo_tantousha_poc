# 層2: タイミングシグナル（インテントデータ分析）

作成: 2026-09-03 ／ 実装: `src/intent/`＋`src/intent-analyze.js` ／ テスト: `npm run test:intent`

## なぜ作るか

層1（ATS未導入 × ICP適合）だけでは母数が大きすぎて刺す順が決まらない。
層2は「**いま採用業務が回っていない／いま採用に投資すると決めた**」痕跡を集め、架電の順番を作る。

## シグナルと重み

| # | シグナル | 重み | 半減期 | 一次情報の在り処 | 履歴が要るか |
|---|---|---|---|---|---|
| 1 | 人事・採用担当の**中途求人** | 40 | 45日 | 求人ボックス（社名×人事/採用担当） | 不要 |
| 2 | 二次募集・秋採用・通年採用への切替 | 28 | 30日 | マイナビ掲載面／自社採用ページ | 不要 |
| 3 | 採用専用メールアドレスの**新設** | 22 | 90日 | 自社サイト（mailto/本文） | **要** |
| 4 | 採用予定数の前年比増 | 20 | 120日 | マイナビ会社概要の採用実績3年系列 | 不要 |
| 5 | 採用ページの新設・リニューアル | 16 | 60日 | 自社採用ページの指紋／媒体面の最終更新日 | **要**（更新日のみ不要） |
| 6 | 採用用LINE公式アカウントの取得 | 14 | 90日 | 自社サイト（`line-official.js`） | **要** |
| 7 | インターン・仕事体験の新規開始 | 10 | 60日 | マイナビ説明会/インターン面のエントリ数 | **要** |
| 8 | 合同説明会の初出展 | 10 | 60日 | 同上 | **要** |

スコア＝ `Σ weight × strength(その社での確からしさ 0..1) × decay(0.5^(検知からの経過日/半減期))`（上限100）。
`monitor/heat.js` と同じ「加点して時間で冷ます」モデルを、シグナル単位に持ち込んでいる。

階層: **A 即架電（40点〜）／ B 今週中（22〜）／ C 監視（10〜）／ D 待機**。
`総合優先度 = インテント×0.55 + アポ期待度×0.45`（タイミングを主、層1の適合を従に置く）。

## 「新設」は履歴がないと言えない（設計上の制約）

③⑤⑥⑦⑧は *前回観測に無く今ある* ことでしか「新設／切替」と言えない。
初回実行は **baseline を敷くだけ** で、レベルは「保有（新設かは履歴待ち）」に留まる。
2回目以降の実行で差分が出た社に、初めて "確定(新設)" が立つ。

`--seed data/leads-consolidated-all.csv` で統合マスタから baseline を敷ける。
ただし **メールが空欄の行は baseline を敷かない**（当時は未収集だっただけの社が全部「新設」に化けるため）。

## 収集系統（1つ落ちても他は動く）

| 系統 | 取得先 | コスト | 得られるシグナル |
|---|---|---|---|
| `csv` | 入力リストが既に持つ事実 | 0 | ④（＋③の保有判定） |
| `mynavi` | 会社概要/説明会/インターン/採用データの4面を素のHTTPで取得 | 約1.5秒/社 | ②④⑤⑦⑧ |
| `site` | 公式URL → 採用ページ（polite.js・robots遵守） | 約8秒/社 | ③⑤⑥ |
| `jobs` | 求人ボックス（社名×人事/採用担当） | 約4〜8秒/社（ホスト直列） | **①** |

`site` / `jobs` は polite.js がホスト単位で直列化するため、**絞ったリストに使う**のが前提。
運用は「全件を `csv,mynavi` で走らせて並べ替え → 上位だけ `jobs` を足す」の2段。

## 使い方

```bash
npm run intent            # 既定リスト(data/leads-fresh-top2000.csv)を csv+mynavi で採点
npm run intent:offline    # ネットワーク0（CSVが持つ事実だけ）
npm run intent:full       # csv+mynavi+site（自社サイトまで見る。遅い）
npm run intent:jobs       # 採点済み上位100社にだけ①（人事の中途求人）を足す
npm run test:intent       # 純ロジックの自己テスト（39ケース）

node src/intent-analyze.js --in data/leads-icp-hire6-500.csv --sources csv,mynavi,jobs --limit 200 --conc 4
```

出力:
- `data/leads-intent-scored.csv` … 総合優先度順。`S1_人事中途求人`〜`S8_合説` に「レベル(点数)」が入る
- `data/intent-hot.md` … 上位N社の「なぜ今か」「根拠」「推奨トーク」
- `data/intent/observations.json` … 観測台帳（次回の差分＝“新設”判定の土台）
- `data/intent/runs/<ts>.json` … 1サイクルの統計（監査用）

## 偽陽性をどう潰しているか（実データで踏んだもの）

| 罠 | 対処 |
|---|---|
| マイナビ全ページのタブ「インターンシップ＆キャリア」でインターンが全社に立つ（実測 12社中9社） | `stripMynaviChrome()` で共通ナビを除去。件数は `.box02`（説明会/仕事体験の1エントリ）の数で数える |
| 「二次募集は行っておりません」「応募受付を停止しています」 | キーワード直後26文字の否定・停止表現で打ち消し |
| 「追加募集は状況により検討します」＝まだ動いていない | 留保表現を検出して強度を半減し、レベルに「検討段階」と明示 |
| 「通年採用」は定型文（偽陽性の主犯） | 強度0.35に固定し、根拠にも「定型文の可能性」と書く |
| 「既卒可」は媒体の掲載バッジでも出る | 強度0.35〜0.45の弱シグナル扱い |
| `email-harvest.classifyRole` は `hr` が語中一致する（`chris@`） | 層2では区切り文字で割ったトークン完全一致だけを採用専用アドレスと見なす |
| 人材紹介会社のCA/RA求人を「人事の中途求人」と誤認 | 職種がエージェント側ロールで、自社採用の文脈が無ければ除外 |
| 求人検索の他社カード混入 | `normCompanyName` で社名一致したカードだけ採用 |

## 実測（2026-09-03 / `data/leads-fresh-top2000.csv` 2,000社を `csv+mynavi` で全件処理・所要6分）

| シグナル | 検知社数 | 内訳 |
|---|---|---|
| ② 二次募集・秋採用 | 1,166 | 確定（二次・追加募集）99／強（秋・冬採用）158／中（第二新卒等）／弱（既卒可バッジ・通年採用） |
| ④ 採用予定数の前年比増 | 1,184 | うち **年6名ラインをまたいだ確定 281社** |
| ⑤ 採用ページ（掲載面の直近更新） | 914 | 全て「弱」（46%が直近14日以内に更新＝ありふれている） |
| ③ 採用専用メール（保有） | 767 | 初回のため全て「弱（新設かは履歴待ち）」 |
| ⑦ インターン新規 | 92 | ⑧ 合説 73 |

階層: **A 162社／B 647／C 751／D 440**（電話番号は2,000社すべて保有）。

**base rate を見て2つ弱めた**（初版は A が248社に膨れて順位が壊れていた）:
- 「既卒可」は45%の社に出る＝掲載バッジ。中(0.45)→弱(0.2〜0.25)。
- 「掲載面が直近14日以内に更新」は46%。中(0.4〜0.5)→弱(0.28〜0.4)。

### ①の追い足し（上位60社に `jobs` を足した実測）

`data/leads-intent-hot-jobs.csv`（`npm run intent:jobs`）: 60社中 **14社**に人事・採用ロールの中途求人。
「採用課長候補 人事部採用課 採用戦略」「人事採用部の求人・サイト運用担当」「採用サポート事務」など、
14件すべて目視で自社の人事求人であることを確認した。

初版は同じ60社で37社ヒットしていたが、**その23社は誤検知**だった。求人ボックスが拾っている
その社自身の新卒求人（"2027 新卒採用 農業協同組合"）が「採用」の2文字で引っかかっていた。
対処: 裸の「採用」では通さず、`人事`等の人事ロール語か「採用＋役割語（担当/企画/広報/課/部…）」のみを通し、
`(20\d{2}|\d{2}卒)\s*新卒採用` 形式の職種は除外した。

> 判定ルールを変えたら **`--reset-store`** で観測台帳を作り直すこと。台帳は未検知シグナルを持ち越すので、
> 誤検知だった分はルールを直しても消えない（この誤検知も台帳に残って気づくのが遅れた）。

その他:
- 採用実績の年系列は `data/hire-count.json` に1,294社ぶん既にあり、うち **621社が直近年で前年増**＝
  ④はネットワーク0で今すぐ効く。
- 求人ボックスの企業名セレクタは `.p-result_companyName` に変わっていた（旧 `.p-result_company` は空振り）。
  `src/scrape-media.js` の既存セレクタも合わせて修正済み。

## 既知の限界

- ①は求人ボックス1媒体のみ。Indeedは403で使えない（`scrape-media.js` の既定でも無効）。
- ③⑤⑥は自社サイトのURLが要る。`data/leads-fresh-top2000.csv` は公式URLが30/2000しかないため、
  `site` 系統を効かせるには先にURL補完（`src/search.js` の `discoverUrl`）が要る。
- ⑦⑧の「新規開始／初出展」は履歴2サイクル目から。1回目は「保有」止まり。
- 採用予定数の前年比増は、マイナビ会社概要の**実績**系列を一次情報にしている（予定は範囲表記で当てにならない）。
  媒体の採用予定人数フィールドの年差分は、観測台帳の前回値との比較で2サイクル目から効く。
