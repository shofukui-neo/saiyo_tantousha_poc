## 総合優先度の定義

```
総合優先度 = (インテントスコア × 0.65 + ICPスコア × 0.35) × 予算係数

  MOCHCA適合判定:  対象外 → 0
                   要確認 → 49 で頭打ち
                   適合   → 100 まで
```

判定も合成も [intent/target-fit.js](../src/intent/target-fit.js) の `targetFit()` **そのものを呼ぶ**。
`build-icp-intent-all.js` は式を写していない。採点済みCSVの列から `evFromRow()` で
取得結果（`ev`）を組み立て直してから渡す（取得はしない）ので、適合判定の定義は1箇所にしかない。

総合ランクの帯は `MOCHICA_PRIORITY_HIGH`(70) / `_MID`(50) に合わせてある。
「要確認」が49で頭打ちなので、**S/A/B は実質「適合が確認できた社」だけ**が入る。

| ランク | 総合優先度 |
|---|---|
| S | 70以上（今週架電） |
| A | 60-69 |
| B | 50-59 |
| C | 49以下（＝要確認の頭打ち帯を含む） |
| 除外 | 0（MOCHCA適合判定が対象外） |

## なぜ2回 ICP を採点するのか

層1は**同じ経路で2回**動く。理由が違う。

### 1回目 `all:icp` — 統合マスタの「アポ期待度」が古い

統合マスタ `leads-consolidated-all.csv` が持つ `アポ期待度` 列は **v4時代に保存された値**で、
21,779社の大半が 100 に張り付いている。総合優先度はこの列を層1として読むので、
ここが定数だと **層1が効かず、実質インテントスコアだけの並び**になる。

`rescore-icp-v5.js` は CSV が持つ事実だけで v5.1 を採点し直し、
`アポ期待度` / `ICPスコア` / `ICPランク` / `MOCHICA適合` / `確信度` / `組織型` / `ICP根拠` を書き戻す。
ネットワークは使わない。

### 2回目 `all:final` — 掲載面で欠測が埋まったあと

v5 の第2段（`p(アポ|接触)`）は **年間新卒採用人数が唯一の軸**だが、統合マスタではこの列がほぼ空で、
1回目の採点では全社が「不明 ×0.93」で横並びになる。

層2を走らせると、その人数が掲載面から実際に埋まる（卒年面の募集人数 → 定着率開示欄の入社実数）。
`build-icp-intent-all.js` はその値を ICP の入力に戻してから採点し直す。
**＝第2段がここで初めて効く。**

充填の優先順は `icp-rules.js` の `resolveIcpInputs()` と揃えてある:

| 軸 | 優先順 |
|---|---|
| 従業員数 | CSV `従業員数` → `従業員数(掲載)` |
| 新卒採用人数 | CSV `年間新卒採用人数` → `新卒規模` → `募集人数(最新卒年)` → `昨年度入社数` → `採用予定人数` |

**範囲表記は下限で取る**（「36～40名」→ 36）。過大評価しないため。

## 走らせていない系統（＝この結果の限界）

全社に当てるにあたり `csv,mynavi,faces` だけを回している。`site` と `jobs`/`midjobs` は入れていない。

| 系統 | 入れなかった理由 | 落ちる軸 |
|---|---|---|
| `jobs` | 求人ボックスがホスト単位で直列化され実測6秒/社。21,779社で36時間超 | **S1 人事・採用担当の中途求人（重み40・最強）** |
| `site` | 自社サイトを持つのが 2,257社（10%）だけで、全社に回すコストに見合わない | S3 採用メール／S6 採用LINE／S9 手作業管理 ほか |
| `midjobs` | 同上（`jobs` と同じホスト） | **S30 新卒中心・採用構成ゲート** |

結果として **採用構成は大半が「不明」＝中途中心ゲートは誰も落としていない**。
`要確認項目` に `中途採用の規模(midjobs未取得)` として出るので、そこを埋めれば精度が上がる。

2周目の想定: 総合優先度の上位だけを `intent:deep:pool` / `intent:mix` に流し、S1 と S30 を立てる。

## 完全新規 / 既存接触の割り

`build-icp-intent-all.js` の出力は統合マスタ全社なので、**大半がすでに触っている社**である。
`split-icp-intent-fresh.js`（`npm run all:split`）が exclusion-index の4層
（MOCHICA顧客430／BALES既存23,152／SFリード86,674／納品済み台帳1,601＝ユニーク57,483社）で割る。

**CSVの `既存被り` 列は信じない。** 統合時点の値で層が欠けており、実測で
総合50以上443社のうち この列だけでは拾えない社があった。索引をその場で組み直す。

## 実走結果（2026-09-18・21,779社・所要88分）

下表は**不整合①②を修正したあとの再集計**（修正前の値は §既知の不整合に残してある）。

### 総合ランク別

| ランク | 社数 | うち完全新規 |
|---|---|---|
| S(70+) | 83 | 3 |
| A(60-69) | 125 | 4 |
| B(50-59) | 162 | 7 |
| C(-49) | 9,998 | 1,977 |
| 除外 | 11,411 | — |

**総合50以上で電話番号があるのは369社、そのうち完全新規は14社**（残り356社は
SF／BALES／MOCHICA顧客のいずれかに接触済み）。
対象外を除いた完全新規は全体で1,991社だが、**その大半は「要確認」で49頭打ち**。

### MOCHICA適合判定別

| 判定 | 社数 |
|---|---|
| 対象外 | 11,411 |

| 理由 | 社数 |
|---|---|
| 新卒N名<6（採用フロア未満） | 10,182 |
| 従業員N名<100（規模フロア未満） | 5,745 |

### 要確認9,790社の穴

| 埋めるべき項目 | 社数 |
|---|---|
| エントリー人数 | 9,790 |
| 業種 | 約7,800 |
| 中途採用の規模（midjobs未取得） | 約7,700 |

エントリー人数は**全社で欠測**（統合マスタに該当列が無い）。架電で聞いて初めて入る値なので、
この列が埋まらない限り9,790社は49で頭打ちのまま＝S/A/B帯に上がれない。

**S30（新卒中心）**が丸ごと落ちている。上位だけ2周目に回して立てるのが次の一手。

S20（初任給の引き上げ）が0なのは系統の問題ではなく、**前年比較の基準が無い初回走行だから**。

## 修正した不整合（2026-09-18）

どちらもこの実走で見つけ、ユーザー判断のうえ `intent/target-fit.js` を直した。
上の実走結果は**修正後の再集計**。

### ① 新卒人数は「今年度の採用目標人数」で見る

同じ「年間新卒採用人数」を、2つの関数が違う優先順で決めていた。

| 関数 | 優先順 |
|---|---|
| `icp-rules.js` `resolveIcpInputs()`（v5.1で追加） | 募集人数 → 入社実績 → 採用予定 |
| `intent/target-fit.js` `targetFit()`（修正前） | **採用実績系列（昨年度の実数）が最優先** |

ゲート判定に使うのは後者だったので、**「28卒は6〜10名募集」だが「昨年度は3名しか入社しなかった」
社が採用フロア未満で対象外**になっていた。実測1,664社が該当し、うち287社は公的・協同組合系
（v5で接触2.1倍・アポ4.4倍＝最も効く層）。

**これは向きが逆だった。** 昨年度の実績が低い社は「計画を充たせなかった社」＝MOCHICAが
いちばん刺さる相手で、実際その事実は S22（昨年度の採用計画が未充足）として**加点**している。
同じ事実でフロアから落とせば、最も熱い層を自分で捨てることになる。

修正: `targetFit` の hire を `resolveIcpInputs()` に一本化（実績系列は最後の手当てとしてのみ残す）。
結果、採用フロア未満での対象外が **11,153社 → 10,182社**（971社が母集団に復帰）。
JAきたそらち・JAあわじ島・社会福祉法人であいの会などが戻った。

ただし**復帰した社はほぼ「要確認」＝49頭打ち**で、S/A/B帯には上がっていない。
業種とエントリー人数が埋まっていないため。

### ② `既存被り` を適合判定のゲートに追加

`targetFit()` が見る除外列は `DNC` / `架電拒否` / `除外フラグ` / `既存顧客` の4つで、
**統合マスタが実際に持っている `既存被り`（`MOCHICA顧客` / `BALES` / `SF`）は見ていなかった**。
結果、既存顧客が 適合 判定で上位に出ていた（**(株)ネオキャリア【BPO事業部】が総合89.5でS帯3位**
＝`既存被り=MOCHICA顧客` かつ自社グループ）。

修正: `既存被り` が `MOCHICA顧客` / `既存顧客` のときだけ対象外にする（**284社**が該当）。
**SF／BALESは落とさない** — 過去に接触しただけで失注ではなく、履歴がある側＝再アプローチの
材料がある層だから。新規/既存の切り分けは `split-icp-intent-fresh.js` が4層索引で後段に割る。

## 注意

1. **総合優先度は受注確率ではない。架電の並び順である。** 学習済みの受注モデルではなく、
   実測フィットの係数（ICP側）と営業仮説（重み0.65/0.35）の合成。
2. **インテント階層は並べ替えに使わない。** 実走で階層Aが13,345社（61%）に膨らんだ。
   `score.js` の閾値（A≥45.4）が21軸時点の目盛りのままで、30軸では較正が合っていない
   （[intent-failure-budget.md](intent-failure-budget.md) 末尾の未了項目）。並びは総合優先度で取る。
3. S2（二次募集・秋採用への切替）が13,205社＝母集団の61%で立っている。
   重みの効き方として広すぎる可能性があり、上位の顔ぶれがこの1軸で決まっている
   （S帯上位の最有力シグナルがほぼS2）。サンプル監査の対象。
4. 採用構成の係数（×1.15 / ×0.55）は**成約実測で検証していない**（`icp-scoring-v5.md` §7c）。
   `ICP_V5_MIX=off` で外せる。
5. **架電禁止リスト `data/ng-companies.txt` が無いとガードは素通しになる**（警告は出る）。
   今回の実走は**全工程でこの警告が出た状態**＝7,191社の禁止リストが一切効いていない。
   納品前に `npm run ng:sync` で復元し、`npm run ng:check` が 0本/0行 であることを必ず確認する。
