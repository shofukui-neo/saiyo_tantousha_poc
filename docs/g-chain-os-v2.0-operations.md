# G-Chain OS v2.0 — 実運用ガイド（リアルタイム営業分析システムとして使う）

> 設計本体: [g-chain-os-v2.0-structured-only.md](g-chain-os-v2.0-structured-only.md)。
> 本書は「実際に日々の営業で使う手順」を定義する。MiiTel不使用。

---

## 0. "リアルタイム" の現実的定義（重要）

BALES/SF は**API非公開**（本システムの制約＝API依存ゼロ）。従って純粋なストリーミングは不可。
本システムの "リアルタイム" は次の2層で成立する：

| 層 | 何がリアルタイムか | 仕組み |
|---|---|---|
| **点（架電の瞬間）** | 1社のスコア・最適時間帯・再活性化・NG警告を**即座に**返す | 事前学習済モデル(`model.json`)を参照。CSV再読込のみ、1秒未満 |
| **面（日次/更新時）** | 母集団全体のキュー・リフトを**当日データで**更新 | BALESを毎朝(または随時)エクスポート→`train`で再学習。`watch`で更新自動検知 |

つまり「モデルは常時即応、データは日次(or手動エクスポート時)更新」。これが到達可能な実運用リアルタイムの上限。

## 1. セットアップ（初回のみ）

```bash
# 1. BALESから全リードをエクスポートし data/ に置く（既存の運用と同じ）
# 2. モデルを学習
npm run gchain:train
#   → data/gchain/model.json 生成（特徴値→成果率の集約のみ・個社情報なし）
```

## 2. 日次ループ（1日10分・仕様の運用原則に準拠）

### 朝（5分）— 本日のコールキューを出す
```bash
npm run gchain:train          # 昨日ぶんの結果を反映して再学習（エクスポート更新後）
npm run gchain:queue -- --limit 50
#   → 高スコア未架電 + 再活性化到来を優先度順に出力
#   → data/gchain/v2/call-queue.csv（種別/アポ期待/再活性/推奨時間帯/理由）
```
このキューの上から架電する。**種別NEW=新規上位、REACTIVATE=今月が旬の再活性化**。

### 架電の瞬間（数秒）— 架電前ブリーフ
```bash
npm run gchain:brief -- "会社名"
```
返るもの（例）:
- アポ期待値（ベース比リフト）・担当接続期待
- スコア寄与（↑↓ どの属性が効いている/不利か）
- **ATS シグナル**（NEXT/sonarATS 等は 2-3x → 強い訴求余地）
- **推奨時間帯**（接続率順）
- **再活性化 優先度**（検討時期・更新月・次アクション日）
- **NG警告**（アプローチ禁止・既存顧客）
- **未消化フォロー**（期限超過の次アクション）
- 一言レコメンド（優先架電 / 時間帯変更 / 再活性化待ち / 対象外）

### 終業（3分）— 結果を戻す
1. 当日の架電結果を BALES に記録（通常運用どおり）
2. BALESを再エクスポート → 翌朝の `train` が拾う

### 常時稼働したい場合（near-real-time）
```bash
npm run gchain:watch
#   BALESエクスポートCSVの更新を監視し、更新のたび自動で再学習＋キュー再生成
```

## 3. 週次ループ（30分）

```bash
npm run gchain:analyze
#   → data/gchain/v2/report.md（接続/リフト/失注/再活性化/行動規律の全体像）
```
週次の使い方（設計 §12 の単一変数PDCA）：
1. **ボトルネック1つ**を接続 or リフトから特定（例：夕方接続率が低い → 架電を午前に寄せる）
2. **失注インテリジェンス**の actionable 分を理由別アクションで潰す（時期相違→再活性化キュー、競合負け→訴求整備）
3. **行動規律**でフォロー実行率/overdue率を確認（自分/所有者別。話し方でなく行動を正す）
4. 変えた1変数の効果を翌週の同レポートで測る

## 4. リスト作成システムへの還元（本システムの最大価値）

```bash
npm run gchain:queue          # scored-uncalled 相当のスコアが付く
#   data/gchain/v2/scored-uncalled.csv（未架電リードのアポ期待値スコア）
```
- 高スコア・高リフトの**セグメント条件**（例：ATS=NEXT/sonarATS、採用11-20名、朝架電、失注リサイクル源）を
  既存のリスト作成システム（`build-*`/`mochica` 系）の**抽出条件・スコア加点**に反映する。
- これで「成果が出た特徴」→「次に作るリスト」への**フィードバックループ**が閉じる（設計 原則9）。

## 5. 本番サーフェス（どこで使うか）の選択肢

| サーフェス | 手段 | 向く場面 |
|---|---|---|
| **ローカルCLI** | `ops.js`（本書） | 単独運用・即使える・PIIがローカルに留まる（推奨の初期形） |
| **Google Sheets** | `apps-script/gchain-os.gs`（v1.5で生成済のGAS層を流用） | チーム共有・BALESをIMPORTRANGE/日次貼付→キューをシート表示 |
| **簡易HTMLダッシュボード** | queue/brief のJSON出力→ローカルHTML | 一覧を見ながら架電したい場合 |

> Sheets本番化：`npm run gchain:build` で `gchain-os.gs` を再生成 → スプレッドシートのApps Scriptに貼付 →
> メニューから日次同期。`ingest-structured` のスコアリングをGAS側`_write01`相当に載せればキューがシート常設になる
> （Sheets I/O列マッピングはWave 0で確定済み＝bales-map）。

## 6. コマンド早見表

| コマンド | 用途 | 頻度 |
|---|---|---|
| `npm run gchain:train` | モデル学習・保存 | 日次(朝) / エクスポート更新時 |
| `npm run gchain:brief -- "会社名"` | 架電前ブリーフ | 架電のたび |
| `npm run gchain:queue -- --limit N` | 本日のコールキュー | 朝 |
| `npm run gchain:watch` | 更新監視→自動再学習 | 常時稼働時 |
| `npm run gchain:analyze` | 週次フル分析レポート | 週次 |

## 7. 運用上の注意

- **出力は全てPII**（社名・成果）を含むため `data/**` gitignore でローカル限定。共有時は会社ドメイン内Sheets/Driveへ（設計 §14 継承）。
- モデルは**過去の実績に基づく**。新規開拓のコールドセグメントは学習外＝スコアが平均付近になる（過小評価しない設計＝log-odds中立）。
- **相関であって因果ではない**。「ATS=NEXTが3x」は「NEXT利用企業が元々MOCHICA適合が高い」可能性を含む。実験(§8)で検証してから大きく振る。
- 再活性化の「失注1年超(減衰)」等は負の理由も併記される。優先度スコアが最終判断。
