# インテントデータ収集の設計（2026-09 改訂）

架電先を「業界で選ぶ」のをやめ、**採用ニーズが発生した瞬間で選ぶ**ための収集基盤。
本書はその収集層（誰から・何を・どう観測するか）の設計と、今回の改訂で何を直したかを残す。

## 改訂前に何が壊れていたか（実測）

| 症状 | 実測値 | 原因 |
|---|---|---|
| シグナル母数が足りない | `releases.jsonl` 154本のみ | 収集ソースが PR TIMES 1本 |
| 取れる企業がICPと合わない | 首位が合同会社のピラティススタジオ | PR TIMES の母集団はスタートアップ／IT に偏る。ICPは**非IT × 従業員300-500名 × 新卒6名以上** |
| 差分シグナルが出ない | 台帳113社・観測1回・全社 `seen:false` | 日次スナップショットを取る経路が無く、「求人急増」「長期掲載」が構造的に発火しない |
| 収集品質を測れない | 不採用理由は画面出力のみ | 規則を変えても採択率の変化を後から検証できない |

要するに **「モデル（判定規則）の問題ではなく、収集ソースがICPと合っていない」** ことが最大の穴だった。

## 改訂後の収集ソース

| ソース | 入口 | 取れるシグナル | ICP適合 | 信頼度 |
|---|---|---|---|---|
| PR TIMES | keyword topic 巡回 | 出来事（新拠点・M&A・資金調達・採用強化…） | 低（IT／スタートアップ偏り） | 0.85 |
| **公式サイト巡回（新規）** | 自社台帳28,000社の公式URL／採用ページ | 出来事＋**ページ指紋の変化** | **高（ICPで母集団を作れる）** | 1.0 |
| 求人媒体スナップショット | `signal-store ingest` | 求人急増／長期掲載／新規掲載／**ベースライン超過** | 高 | 1.0 |

第三者Intent（Bombora/G2 等）を買う前に、**自前の一次観測を基準値にする**という順序を取る。
`watchlist` は 21,017社（非IT×URL保有）、うち自社サイトを持つのが 1,846社。

## 収集の作法

- 取得は全て `polite.js` 経由（robots.txt 遵守・ホスト別レート制限・ディスクキャッシュ）
- 1社あたり最大4ページ。サイト全体は舐めない（トップ → 採用 → ニュース の1ホップのみ）
- 本文は保存しない。指紋（SHA1の先頭16桁）と根拠文だけを残す

## 企業サイト収集の肝 —「日付つきの出来事」だけを判定に回す

プレスリリースは全文が1つの出来事だが、企業サイトの本文は**大半が恒常的な説明文**で出来事ではない。
`detectSignals` をページ全文に当てた初回実測は次のように総崩れになった。

| 本文 | 誤検出 | 実体 |
|---|---|---|
| 1984年12月 第二工場竣工 | 新工場OPEN | 40年前の沿革 |
| 東京・宮城・栃木にも拠点を展開しています | 新拠点開設 | 会社紹介 |
| 【新入社員研修】入社式後、約2か月間の… | 通常採用活動 | 制度の説明 |

対策として `extractDatedItems()` を入れ、**日付から次の日付まで**を1件の出来事として切り出し、
その単位でだけ判定する。副産物として各シグナルに正しい発生日が付き、鮮度係数がそのまま効く
（沿革表の古い年は鮮度窓の外に落ちる）。同じ12社での採択率は 66.7% → 16.7% に下がったが、
残ったものは全て実在の出来事だった（誤爆を数えていたのが前者）。

## スコアへの反映

基礎点 = Σ（熱度点 × 鮮度 × 逓減 × **ソース信頼度**）に加えて、

- **連鎖（Sequence）** … 資金調達→大量求人開始 のように原因と結果が揃う組み合わせに加点（`COMBOS`）
- **継続（Frequency）** … 別々の日に3本以上observedなら加点（一過性の広報ではない）
- **多源（Identity confidence）** … 2ソース以上が同じ社を指していれば加点
- **ベースライン偏差** … 直近3週の平均求人数 vs 過去12週の平均。1点比較の揺れを均す

## 監査（収集品質を測る）

全判定を `data/hot-signals/audit/YYYY-MM.jsonl` に追記する（採択／不採用と理由）。

```
npm run hot:audit           # ソース別の採択率・不採用理由の内訳
npm run hot:audit:sample    # 採択分を無作為抽出（人手で○×を付ければ Precision の実測になる）
```

## 日次の回し方

```
npm run hot:harvest    # PR TIMES から出来事を収集
npm run hot:site       # 自社ICP企業300社を巡回（ローテーション：21,017社を約70日で一周）
npm run hot            # 採点＋除外突合 → data/leads-hotlead-YYYYMMDD.csv
npm run hot:daily      # 上記をまとめて実行し、納品台帳へ記録
```

**巡回2周目から本領を発揮する**。1周目は指紋を置くだけで差分シグナルが0になる
（`npm run hot:site:stats` で「指紋を保持N社＝差分が出せる社数」を確認できる）。

## 残っている課題

- 求人媒体スナップショット（`signal-store ingest`）を日次で回す経路がまだ手動。マイナビ側は
  Playwright が要るため `scrape-mynavi` 系との接続が必要
- 採択したシグナルに対する**成果（アポ／商談）の紐づけ**が無く、ソース別の実効Precisionを
  実測できていない。監査ログにアポ結果を突き合わせるのが次の一手
