# 企業の公式LINE利用有無 判定機構

## なぜ作ったか

接続後お断り理由の第2位が **「公式LINE使ってるから足りてる」（445件・7.2%）**
（[分析-接続後断り理由とアポ獲得トーク.md](分析-接続後断り理由とアポ獲得トーク.md) シーン②）。
この断りの正体は「公式LINE（一斉配信）」と「MOCHICA（個別の選考進捗・歩留管理）」の混同で、
克服トークは実在する。ただし **架電中に初めて「LINE使ってます」と言われてから切り替える** ので後手に回る。

相手が公式LINEを持っているか／何に使っているかを **架電前に** 知っていれば、

| 判定 | 架けるトーク |
|---|---|
| 有・用途=採用 | 最初から役割差（配信 vs 個別の歩留管理）で入る |
| 有・用途=販促/顧客 | 「そのLINEを採用の歩留に」と地続きで提案する |
| 有・用途=不明 | 「LINEは何にお使いですか」を一問置いてから分岐 |
| 要確認 | 冒頭で「公式LINEは使われていますか」を確認してから分岐 |
| 無 | LINEを主語にしない（母集団・歩留を主語に。LINE推しは逆効果） |

を **リストの列として** 持ち込める。判定結果はそのまま `LINEトーク指針` 列に文章で入る。

## 使い方

```bash
# 1社だけ確認（デバッグ・スポット調査）
npm run line:probe -- "会社名" "https://公式URL/" --verify
node src/probe-line.js "ヤマト運輸" "https://www.kuronekoyamato.co.jp/" --verify --fresh

# リストに列を付与（既定は data/leads-icp-hire6-500.csv を上書き更新）
npm run line -- --in data/leads-icp-hire6-500.csv
npm run line -- --in <入力.csv> --out <出力.csv> --conc 5 --verify --limit 50

# ロジックのテスト（ネット不要・20ケース）
npm run test:line
```

主なオプション

| フラグ | 効果 |
|---|---|
| `--verify` | `page.line.me/{id}` を叩いて **@IDが実在するか** まで確認（確度95まで上がる。1社あたり数秒増） |
| `--render` | 静的HTMLが薄いJS描画サイトをブラウザ描画して見る（精度↑・重い。既定OFF＝メモリ枯渇回避） |
| `--refresh` | 台帳・キャッシュを無視して取り直す |
| `--limit N` | 先頭N社だけ（試走） |
| `--max-pages N` | 1社あたりの深掘り上限（既定6） |

大量処理時は取得待ちが支配的なので `SCRAPE_MAX_RETRY=1 PER_PAGE_TIMEOUT_MS=8000 SCRAPE_DELAY_MS=1500` を付ける。

## 付与される列

`公式LINE` / `LINE確度` / `LINE ID` / `LINE URL` / `LINE用途` / `LINEトーク指針` / `LINE根拠` / `LINE検査日`

`公式LINE` は **有 / 無 / 要確認 / 不明** の4値。「無」と「不明（取得できなかった）」を混ぜないのが要点で、
不明はトーク分岐の材料にしてはいけない（架電前に断定すると外す）。

結果は `data/line-official.json`（台帳）に社単位で貯まり、**別のリストに同じ社が出てきたら再取得しない**。

## 判定の作り

3層。判定ロジック（純関数）と取得（ネット）を分けてあるのでテストが回る。

| ファイル | 役割 |
|---|---|
| `src/line-official.js` | 判定エンジン（純ロジック・ネット不要）。HTML→証跡→判定 |
| `src/probe-line.js` | 取得層。どのページを見るか、www補正、lin.ee展開、実在検証 |
| `src/enrich-line-official.js` | リスト運用層。CSVに列付与・台帳・再開・サマリ |
| `test/line-official.test.js` | 20ケース（真陽性5・誤検知トラップ4・集約4・巡回選定3ほか） |

### 証跡（強い順）

| level | 種類 | 例 |
|---|---|---|
| 3 | 友だち追加リンク / 公式アカウントページ / 公式QR / OA管理画面 | `line.me/R/ti/p/@id`、`page.line.me/id`、`qr-official.line.me/...` |
| 2 | lin.ee短縮リンク / LIFF / 「LINE公式アカウント」「友だち追加」「LINEでお問い合わせ」等の文言 | `lin.ee/xxxx`、`liff.line.me/...` |
| 1 | LINEログイン連携 / 個人LINE ID(`~`) / 「LINEで配信」等の弱い文言 | → **要確認** 止まり |

level2以上で「有」、1で「要確認」、証跡ゼロかつ1ページ以上取得できたら「無」、1ページも取れなければ「不明」。

### 誤検知として明示的に落としているもの

1. **記事の「LINEで送る」シェアボタン**（`social-plugins.line.me/lineit`、`line.me/R/msg/text`）
   … 自社アカウントの証跡ではない。むしろ「無」の材料として根拠欄に出す。ここを取り違えると全社が「有」になる。
2. **LINE WORKS**（社内チャット）… 公式アカウントとは別物。
3. **英単語の LINE**（ONLINE / LINE UP / PRODUCT LINE / 生産ライン / ラインナップ）
   … 語境界つきで拾い、否定語で再度落とす。

### 用途（採用 or 販促・顧客）の決め方

**リンクの周辺文脈だけ** から採る。ページURLからは採らない。
実データで踏んだ罠がこれで、ヤマト運輸は全ページ共通フッターのSNSアイコンにLINEがあり、
それが採用ページにも出るため「ページURLが `/recruit/` だから採用用途」と誤断していた。
現在はフッター/SNSアイコン列（祖先要素のclass/idで判定）由来の証跡を用途推定から除外し、
文脈が無ければ「その口座が採用面にしか出ていない」時に限って採用と見なす。それ以外は正直に「不明」。

### 巡回するページ

トップ → SNS/フォロー面 → お問い合わせ → 採用/エントリー → お知らせ → 会社概要 の優先順で最大6ページ。
**level3の確実証跡が出た時点で打ち切る**（「無」を主張する時だけ全部見る＝コストを判定の難しさに比例させる）。

- 深掘りは公式URLと同一ドメインのみ。別ドメインの自社採用サイトは種として追加するが、
  **求人媒体ドメイン（マイナビ等）は必ず除外**する（媒体面のLINEリンクは媒体自身のもの）。
- 公式URLが取れなかった時は www の有無を入れ替えて1回だけ再試行する
  （例: `show-wa.co.jp` はNG／`www.show-wa.co.jp` はOK。入れないと「不明」が水増しされる）。
- 取得はすべて `polite.js` 経由（robots.txt遵守・ホスト別レート制限・ディスクキャッシュ）。
  `line.me` の robots は `/R/ti/p/` と `page.line.me` を許可しているので、実在検証も規約内。

## 既知の制約

- **公式URLが無い社は判定できない。** `data/leads-icp-hire6-500.csv` は329/500社が公式URL空
  （採用ページURLがマイナビのみ）で、この列を埋めるのが先。統合マスタ `leads-consolidated-all.csv`
  でも公式URL保有は18.6%（5,631/30,290社）。**公式LINE判定のカバレッジ＝公式URLのカバレッジ**。
- 「無」は「サイト上に証跡が無い」であって「アカウントを持っていない」の証明ではない
  （店舗限定運用・紙のQRのみ等）。だから確度は最大80止まりにしてある。
- JS描画サイトは `--render` を付けないと本文が取れない社がある（既定OFFはメモリ対策）。
