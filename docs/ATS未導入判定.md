# 全リード企業の「ATS未導入」判定機構

## なぜ作ったか

MOCHICA顧客429社の全数調査で、受注に効く要因の実測トップが
**「他社ATS未導入」（勝率2.8倍差）** だった（[mochica-win-drivers](../data/mochica-win-analysis.md)）。
つまり統合マスタ30,290社を「ATSを持っていない企業」に絞れるだけで、架電の期待値が変わる。

さらに未導入の中でも、**どうやってエントリーを受けているか** で刺さり方がまったく違う。
そこで判定は有無の2値では終わらせず、**エントリー動線の型（`entry_type`）を1フィールドに落とす**。

| entry_type | 意味 | 重症度 | 架電の入口 |
|---|---|---|---|
| `pdf_download` | エントリーシートをPDFでDLさせる | 5 | 「集めた後の集計と連絡、今どなたが？」最重症・提案が刺さる |
| `phone_only` | 説明会予約が電話番号のみ | 5 | 「夜間・土日の予約が拾えていない」取りこぼしが最大 |
| `mail_direct` | エントリーがメールアドレス直記載 | 4 | 「応募メール、何時間以内に返せていますか」 |
| `google_form` | Googleフォームに飛ぶ | 4 | 「スプレッドシートの後工程」が全部手作業 |
| `generic_form` | 汎用フォームSaaS（自前辞書がATSでないと判定） | 3 | 「フォームの後、進捗はどこで管理を？」 |
| `media_only` | マイナビ/リクナビの掲載ページにしか導線がない | 3 | 「媒体が切れた後の再アプローチ」 |
| `own_form` | 自社ドメイン内の応募フォーム | 2 | 未導入だが痛みは弱い。母集団・歩留から |
| `ats_vendor` | 外部ベンダーのドメインに飛ぶ | 0 | **除外**（乗り換え時期狙いなら別トーク） |
| `none` | 動線が見つからない | 1 | 判定材料にしない |

`pdf_download` `phone_only` `mail_direct` `google_form` `media_only` `ats_vendor` が営業要件の6分類。
`generic_form` / `own_form` / `none` は **6分類に押し込むと精度が壊れるので別に立てた残余**で、
`ats_vendor` 以外はすべて「ATS未導入」側に入る。

## ベンダー指紋を外から拾ってこない

`ats-detect.js` には **ベンダー名もベンダーのドメインも1つも書いていない**。判定に使うのは構造だけ:

> エントリー文脈のリンクが、自社ドメインの外に出ているか

外に出た先が何者かは、自前で学習した辞書 `data/ats-fingerprints.json` に問い合わせる。
辞書は次の2つ **だけ** から作る。

**① 多テナント性** — 無関係な複数企業のエントリー導線が同じホストに集まる。これは定義上ベンダー。
ラベルが1件も無くても検出できる（＝運用して台帳が貯まるほど辞書が自分で育つ）。

**② 自社データの正解ラベル** — BALESCLOUDリード22,892件の `カスタム情報：利用中ATS`。
インサイドセールスが架電時に本人から聞き取った自己申告で、分布は

```
無し 16,967 ／ 採用一括かんりくん 504 ／ sonarATS 260 ／ キャリタスContact 168
／ AOL 127 ／ NEXT 102 ／ 管理くん 101 ／ i-web 89 ／ HRMOS 65 …
```

Webサイト付きでユニーク化すると **陽性889社・陰性8,745社**。ここに MOCHICA既存顧客429社を
統合マスタ経由でURL突合したものを「MOCHICA導入済」の陽性として足す。

ラベルは2つの役割を持つ。**ベンダー名の確定** と、**ATSか単なる汎用フォームSaaSかの判別**。
あるホストに集まった企業の申告が「無し」ばかりなら、そのホストは `side='diy'`（未導入側）に落とす。
これをやらないと、フォームツールを全部ATS扱いして未導入企業を取りこぼす。

> なお **SFリード86,610件はこの層では使えない**。実データを確認したところ、
> 会社名・電話・姓・採用人数・リード状況のみで、ATS列もWebサイト列も持っていない。
> ATSの正解ラベルを持っているのはBALES側だけ。

## 使い方

```bash
# 0) 指紋辞書を作る（最初に1回。以後は運用で育てる）
npm run ats:learn                        # 既定 train140 / test90
npm run ats:learn -- --train 200 --test 120 --conc 8

# 1) 1社だけ確認（デバッグ・スポット調査）
npm run ats:probe -- "会社名" "https://公式URL/" --max 6
node src/probe-ats.js "株式会社マンダム" "https://www.mandom.co.jp/" --fresh

# 2) リストに列を付与
npm run ats -- --in data/leads-icp-hire6-500.csv
npm run ats:master                       # 統合マスタ30,290社に付与（長時間）
npm run ats -- --in <入力.csv> --out <出力.csv> --conc 8 --limit 200 --only-callable

# 3) 台帳が貯まったら辞書を育て直す（多テナント性は母数が効く）
npm run ats:learn:ledger

# ロジックのテスト（ネット不要・31ケース）
npm run test:ats
```

大量処理時は取得待ちが支配的なので
`SCRAPE_MAX_RETRY=1 PER_PAGE_TIMEOUT_MS=8000 SCRAPE_DELAY_MS=1500` を付ける。

主なオプション（`src/enrich-ats.js`）

| フラグ | 効果 |
|---|---|
| `--only-callable` | 電話番号のある社だけ処理（架電対象に絞って回す） |
| `--max-pages N` | 1社あたりの深掘り上限（既定5） |
| `--refresh` | 台帳・キャッシュを無視して取り直す |
| `--limit N` | 先頭N社だけ（試走） |
| `--render` | JS描画サイトをブラウザ描画（精度↑・重い。既定OFF） |

## 付与される列

`ATS判定` / `ATS確度` / `entry_type` / `entry_host` / `ATSベンダー` / `ATS重症度` /
`エントリー動線` / `ATSトーク指針` / `ATS根拠` / `ATS検査日`

`ATS判定` は **未導入 / 導入済 / 要確認 / 不明** の4値。

- **未導入** … 動線を掴んだ上でベンダー遷移が1本も無かった。架電対象
- **導入済** … 辞書で確定したベンダーへ遷移する導線がある。除外
- **要確認** … 外部ホストへ遷移するが、それが何かを辞書がまだ知らない。**未導入と言い切らない**
- **不明** … 取得できなかった／動線が見つからなかった。トーク分岐の材料にしてはいけない

「未導入」と「不明」を混ぜないのが要点。不明を未導入に足すと架電効率の見積もりが崩れる。

結果は `data/ats-status.json`（台帳）に社単位で貯まり、**別のリストに同じ社が出てきたら再取得しない**。
台帳には判定結果だけでなく証跡（signals）も残るので、`ats:learn:ledger` で辞書を作り直せる。

## 判定の作り

4層。判定ロジック（純関数）と取得（ネット）を分けてあるのでテストが回る。

| 層 | ファイル | 役割 |
|---|---|---|
| 層0 指紋学習 | [src/learn-ats-fingerprints.js](../src/learn-ats-fingerprints.js) | 自社ラベル＋多テナント性から `data/ats-fingerprints.json` を作り、精度を測る |
| 層1 判定 | [src/ats-detect.js](../src/ats-detect.js) | HTML → 証跡 → `entry_type`。ネット不要の純関数 |
| 層2 取得 | [src/probe-ats.js](../src/probe-ats.js) | トップ→採用→エントリーの2ホップ巡回。polite.js経由（robots遵守） |
| 層3 運用 | [src/enrich-ats.js](../src/enrich-ats.js) | 任意CSVに列付与・台帳・再開 |

### 巡回の設計

トップ → 採用トップ → **エントリー/募集要項/説明会** の2ホップ。
1ホップ目の採用トップには「エントリーはこちら」ボタンしか無く、
実体（Googleフォーム/ベンダー/メール）は2ホップ目に出る。ここを取らないと `entry_type` が全部 `none` になる。

打ち切りは非対称にしてある。**辞書で確定したベンダー導線を1本掴んだ時点で終了**（除外が確定するので以降は無駄）。
逆に「未導入」と言い切る時だけ全ページ見る＝コストを主張の重さに比例させる。

### 誤検知を落としている箇所

- **`own_form` の暴発** … 内部リンクは全て自社ドメインなので、エントリー文脈が無ければ動線として採らない。
  これを入れないと1ページ100件超の `own_form` が湧く（実サイトで確認済み）
- **電話番号** … どのページにも載っているので、`phone_only` は他に動線が1つも無い時だけ主動線にする
- **PDF** … 会社案内・IR資料を拾わないよう、エントリーシート系の語に当たるPDFだけを `pdf_download` にする
- **検索フォーム** … `<form action>` はエントリー語彙がある時だけ動線として扱う
- **フォームSaaSのATS誤認** … ラベルが「無し」に偏るホストは `side='diy'` に落とす（未導入側に残す）
- **辞書未収載の外部ホスト** … 「導入済」と断定せず **要確認** で止める。誤除外は良質リードの喪失に直結する

## 精度検証（実測）

`npm run ats:learn` は企業単位で train / test に分け、**train だけで辞書を作り、test で測る**。
train / test はどちらも陽性・陰性を半々で持つ（test に陰性が無いと「未導入と判定した時の正しさ」が測れない）。
結果は [data/ats-fingerprints-report.md](../data/ats-fingerprints-report.md) に混同行列つきで出る。

**2026-09-02 実測（train 200社 / test 140社・ラベル付きの実企業をクロール）**

| 指標 | 値 |
|---|---|
| 未導入判定の精度（**実母集団に引き直し**） | **92%** |
| 未導入判定の精度（test母集団=陽性50%） | 54% |
| 導入済判定の精度 | 63% |
| ATS保有社を除外できた率（再現） | 7% |
| 判定率（導入済/未導入まで言い切れた割合） | 46% |

### 92% と 54% の違い（読み間違えると判断を誤る）

test はロジック比較のために陽性・陰性を半々にしてある。
だが実際のリード母集団のATS保有率は自社ラベル実測で **9.9%**（陽性951社 / 陰性8,685社）しかない。
条件付き率（真の未導入社を未導入と言えた率／ATS保有社を誤って未導入と言った率）は母集団に依存しないので、
そこから保有率9.9%に引き直すと **未導入判定の精度は92%**。
運用でリストを絞る時はこちらの数字で見る。レポートは保有率5%〜50%の感度表も出す。

### 何ができていないか

**再現（ATS保有社の除外）は7%しかない。** 辞書がまだ4ホストしか確定していないため。
つまり現状の価値は「ATS保有社を漏れなく除外する」ことではなく、
**未導入と言い切れた社は高確度で本当に未導入**（＝そこから架電すれば当たる）ことにある。
再現は辞書が育つほど上がる（下の自己強化ループ）。

**真値の限界も承知しておくこと。** ラベルは架電時点の自己申告、サイトは現在時点。
申告後に導入した企業は「誤り」に見える。申告そのものも担当者の認識に依存する
（媒体の管理画面をATSと呼ぶ人もいれば、呼ばない人もいる）。
絶対値ではなく **ロジックを変えた時の相対比較** として読むのが正しい。

### 較正の過程で潰した誤り（同じ罠を踏まないため）

実企業340社をクロールして測ったからこそ出てきた欠陥。いずれも初期実装では気付けなかった。

| 症状 | 真因 | 対処 |
|---|---|---|
| 1ページに証跡が107件湧く | 内部リンクが全て `own_form` になっていた | エントリー文脈のある内部リンクだけ採る |
| 地図・プライバシーマーク・YouTubeがベンダー認定される | 周辺ブロックのテキストで文脈判定していた | 外部ホストは**アンカー文言/href自身**にエントリー語彙がある時のみ |
| 「導入済→未導入」の誤判定がほぼ全部 `own_form` | `<a href="/recruit/entry">` を受付の実体とみなしていた | 実体（フォーム送信先/メール/ES/媒体）が無ければ**不明**に落とす |
| Microsoft FormsがATS扱いされかける | ラベルは企業に付いていてホストには付いていない | ホスト名と申告ベンダー名の**一致検査**を通す（hrmos.co↔HRMOS、snar.jp↔sonarATS） |
| 古い基準で付いた誤指紋が世代を越えて生き残る | 過去辞書を無条件マージしていた | 引継ぎに品質ゲート（エントリー文脈1社以上） |
| 公式URLがマイナビのページの社で全リンクが自社扱い | ベースホストが媒体だった | ベースホストが媒体なら自社ドメイン不明として扱う |
| 採用サイト自体がベンダーのドメイン | サイト内リンクしか見ておらずベンダー遷移が観測できない | ベースホスト自体を辞書に照会 |
| 媒体ページ上で96/100社が `media_only` になる | 媒体自身のUI（お気に入り/エントリー予約一覧）を企業の導線と誤認 | 媒体ページ上の同一媒体リンクは動線にしない |
| SpeakerDeck/Vimeoが「エントリー先」になる（実測39社） | iframe埋め込みを無条件に動線扱いしていた | iframeは正体が判るもの（Googleフォーム/辞書収載）だけ |
| お知らせ欄の代表電話が `phone_only` になる | エントリー窓(±200字)のどこかに番号があれば採っていた | 番号の±45字に受付動詞と用件語の両方を要求 |
| 母数が増えると確定済ベンダーが `unknown` に落ちる | 引継ぎで新しい判定を優先し過ぎた | 名称一致で確定した `ats` は根拠不足では降格させない |

## 実運用の結果（2026-09-02・600社）

統合マスタ30,290社のうち **自社サイトのURLが判っている社に対してだけ判定できる**。
実測でその条件を満たすのは 3,273社、電話番号もある社は 2,052社。
そのうち期待度上位600社を処理した結果:

| ATS判定 | 社数 | 割合 |
|---|---|---|
| 未導入（架電対象） | 230 | 38% |
| 導入済（除外） | 34 | 6% |
| 要確認 | 68 | 11% |
| 不明 | 268 | 45% |

未導入230社の内訳（重症度順に架電すればよい）

| entry_type | 社数 | 重症度 |
|---|---|---|
| `own_form` | 127 | 2 |
| `mail_direct` | 57 | 4 |
| `media_only` | 24 | 3 |
| `phone_only` | 11 | 5 |
| `google_form` | 6 | 4 |
| `pdf_download` | 5 | 5 |

→ 出力: `data/leads-ats-callable.csv`（重症度5が16社、4が63社）

**「不明」が45%と多いのは意図的**。エントリー受付の実体（フォーム送信先/メール/ES/媒体）を
観測できなかった社を未導入に混ぜていないから。混ぜれば数は増えるが、
架電効率の見積もりが崩れて営業の信頼を失う。不明は `--max-pages` を増やすか `--render` で再取得すれば減る。

### 最大の制約は判定ロジックではなく「公式URLの欠損」

統合マスタ30,290社のうち自社ドメインの公式URLがあるのは **3,273社（10.8%）** だけ。
残りはURL未取得（24,659社）か、公式URL列に媒体ページが入っている（2,358社）。
**ATS判定のカバレッジ上限を決めているのはここ**であって、判定ロジックの精度ではない。
全社に付けたいなら先にURL補完（`npm run app` の公式URL解決経路）を回す必要がある。

なお公式URL列が媒体ページの社は、媒体ページから自社サイトを解決して本体を見に行く
（解決できなければ「公式URLが媒体ページ・自社サイト未特定」と根拠に明記して不明にする）。
マイナビの会社概要ページは静的HTMLに自社サイトへのリンクを持たないため、実際には解決できないことが多い。

## 自己強化ループ（再現を上げる唯一の経路）

```
enrich-ats（リストに付与）
      ↓ 台帳 data/ats-status.json に証跡が貯まる
learn-ats-fingerprints --from-ledger
      ↓ 多テナント性が母数で効く。台帳の社名は自社ラベルにも突合される
      ↓ 正体不明でも多テナントなホストは「要レビュー」に並ぶ
data/ats-fingerprints-manual.json に人が side を書く（1ホスト=数分）
      ↓ 再学習で重ねる（生成物は直接編集しない）
enrich-ats（要確認の社だけ再判定）
```

**辞書1ホストの確定が、要確認だった数十〜数百社をまとめて解く。**
レポートの「要レビュー」節が、確定させる価値の高い順に並んでいる。

外部記事に頼っていないので、この精度改善は全部自分の手の中で完結する。
逆に言えば、**辞書を育てなければ再現は上がらない**。ここは運用でしか埋まらない。
