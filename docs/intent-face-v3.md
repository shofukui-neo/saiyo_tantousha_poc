# インテント取得の拡大 v3（幅21軸 × 件数20,928社）

2026-09-15。層2（タイミングシグナル）を **幅**（16軸→21軸）と **件数**（2,579社→20,928社）の
両方向に広げた。実装は `src/intent/mynavi-face.js`（掲載面の構造化）、
`src/intent/face-signals.js`（追加5軸）、`src/build-intent-pool.js`（母集団づくり）。

## 何が制約だったか

| | v2 まで | 何が本当の制約だったか |
|---|---|---|
| 幅 | 16軸。実際に立つのは6軸 | 掲載面を1本のテキストに潰して語を探していた。**募集人数・選考フロー・エントリー方法・初任給は構造値なのに、構造として読んでいなかった** |
| 幅 | 「新設・切替」は観測台帳が2周するまで言えない | corpID が卒年をまたいで安定している事実を使っていなかった。**27卒面と28卒面を今日まとめて取れば、履歴ゼロでも前年比が言える** |
| 件数 | 1,700〜2,600社 | 取りに行けなかったのではなく、入力を納品リストに絞っていただけ。統合マスタ28,129社のうち**18,478社はマイナビ corpID を持つ** |
| 件数 | 2万社を流すと落ちる | 根拠本文をCSVに直書きしていた（実測 11KB/社 → 2万社で200MB超）。さらに50社ごとに全件ソートして全文再書き出ししていた |

## 追加した5軸（S17〜S21）

| 列 | 分析対象 | 重み | 半減期 | 一次情報 |
|---|---|---:|---:|---|
| S17_手作業応募 | 応募受付が手作業動線（メール・電話・郵送・FAX） | 26 | 120日 | エントリー方法欄 |
| S18_次年度面始動 | 次年度卒面を現行面より先行して更新 | 24 | 30日 | 各卒年面の最終更新日 |
| S19_多段選考 | 選考フローの段数・面接回数 | 18 | 150日 | 採用フロー欄 |
| S20_初任給引上げ | 初任給の増額（**要履歴**） | 18 | 150日 | 採用後の待遇欄 |
| S21_コース複線 | 募集コースの本数・増加 | 14 | 150日 | 募集コース欄 |

加えて、既存の **S4（採用予定数の前年比増）に卒年面どうしの募集人数差**を与えた。
これにより観測が1周もしていない社でも初回から前年比を判定できる。
優先順は「採用実績の年系列 → 卒年面の募集人数 → 観測台帳の前回値」。

## 実測した基準率と、それによる較正

200社（統合マスタから等間隔抽出・2026-09-14実測）での検知率。
**最頻値をシグナルにすると順位が作れない**ため、初版の閾値はこの実測で引き上げた。

| 軸 | 初版 | 較正後 | 較正の理由 |
|---|---:|---:|---|
| S17_手作業応募 | 0.5% | 0.5% | 稀であることがそのまま価値。据え置き |
| S18_次年度面始動 | 40% | 27% | 「直近21日以内に更新」は S5（掲載面を直近更新）と同じ事実の二度数え。**現行面より新しい場合だけ**に限定 |
| S19_多段選考 | 38.5% | 15% | 選考段数は4段が最頻（56社/28%）。4段を外し、**5段以上または面接3回以上**に限定 |
| S21_コース複線 | 15.5% | 15.5% | 据え置き |

A階層（即架電）は 59社(29.5%) → 38社(19%) に絞られた。

### S20 が初回に立たないのは仕様

初任給欄は「2025年04月実績」のように**前年の実績**として書かれ、マイナビは次年度面にも
同じ数字をそのまま載せる。実測（両面で金額が取れた19社）で**卒年面どうしの差は全社ゼロ**だった。
したがって2面の比較では原理的に検知できない。比較相手は観測台帳（前回サイクルの記録額）とし、
既存の S3/S5/S6 と同じ「要履歴」型にしてある。初回観測では0件で正しく、
金額が動いた次サイクルから立つ。

## 途中で見つかった既存不具合（幅を広げた副産物）

卒年面を取りに行くようになって、**現行卒年の面だけを見ていたせいの取りこぼし**が2つ出た。

### インターン検知が9月なのに1.5%しかなかった

`is.html`（インターンシップ＆キャリア）は**現行卒年の面には存在しない**。
実測で 27卒面 0/40、28卒面 10/15。インターンは「次の卒年の学生」に向けて開くものなので、
掲載も次年度面にしかない。取りに行く卒年を間違えていた。

さらに `is.html` は説明会面と違って `.box02` のカセット構造を持たない（実DOMで0件）。
プログラム1本につき1回出る見出し「開催時期と実施日数」を数えるよう直した。

S7（インターン・仕事体験の新規開始）の検知: **200社中3社 → 30社**。

### 数え方を変えた履歴と比べると、全社が「新規開始」に化ける

差分シグナルは前回値との比較で立つ。数え方を変えたのに古い記録を残すと
「変わっていないのに変わった」になる。旧ルールで0件と記録された**3,202社**が
一斉に「インターンを新規開始」に化けるところだった。

観測台帳のインターン件数に**版**を刻み、版が違う記録は「履歴なし」として扱うようにした
（＝次の観測から比較を始める）。`src/intent/store.js` の `INTERN_RULE`。

## 誤検知対策（実ページで踏んだもの）

- **タブのナビ列を本文と取り違えない**。マイナビは「募集コース／募集対象／採用フロー／採用後の待遇」を
  全ページのタブとして出す。素直に見出し検索すると全社が「コース1本」に潰れる。
  見出しの本体は必ず「コース名」か「配属職種」を伴うので、それを目印に本体側の出現を選ぶ。
- **区間を切る語を見出しごとに変える**。初任給の表は内側に「諸手当」を含むため、共通の見出し集合で
  切ると金額の手前で区間が終わる。募集コース表は説明文に「福利厚生」を含む。
- **範囲の人数を連結しない**。「26～30名」は下限26・上限30として保持し、比較には**下限**を使う
  （上振れ表記で増加を作らない）。「若干名」は1名、「未定」は欠測として扱う。
- **敬語の接頭辞を許す**。「メールにて**ご**応募ください」を取りこぼさない。
- **面接回数は実ブロックを数える**。「面接（個別）／開催回数／1回実施予定」の並びを足し上げ、
  「複数回実施予定」は回数無記載なので最低2回として数える（過大に見積もらない）。

## 件数の拡大

```
npm run intent:pool      # 統合マスタ → data/intent-pool.csv（採点しに行ける社だけ）
npm run intent:wide      # 20,928社を21軸で採点（約90分・--resume 付き）
npm run intent:finalize  # ↑の最後の書き出しだけが落ちた時の出口（取得はやり直さない）
npm run intent:rescore   # 重み・閾値を直した後、取得し直さずに採点だけやり直す
```

`build-intent-pool.js` は社ごとに**実際に効く取得系統**を判定して `取得可能系統` 列に残す。
「採点したが薄かった」のか「そもそも取りに行けなかった」のかを後から切り分けるため。

| 統合マスタ 28,129社 | |
|---|---:|
| 名寄せ重複で除外 | 773 |
| 取得系統なしで除外（URLも社名も無い） | 6,428 |
| **母集団** | **20,928** |
| うちマイナビ掲載面あり（卒年面5軸が動く） | 18,478 |
| うち自社サイトあり | 2,882 |

### 2万社を流すための作り

- **根拠本文は別ファイル**（`--evidence auto`）。母集団が3,000社を超えたら自動で
  `<out>.evidence.jsonl` に逃がし、CSVには根拠URLと引用だけを残す。
- **完了した社はその場で作業ファイルに追記**。メモリには並べ替えに必要な行しか持たず、
  最終CSVは作業ファイルを読み直して作る。50社ごとに全件を再書き出しする従来の挙動をやめた。
- **`--resume`**。中断しても作業ファイルの済みを読んで続きから流せる。
  最終CSVを書けた時点で作業ファイルは片付ける。
  （検証: 30社の入力に12社ぶんの作業ファイルを残して再開 → 18社だけ処理し、
  出力30行・重複0・No連番。）
- **観測台帳の途中保存**（`--store-every`、既定2000社）。従来は実行の最後にしか
  書いておらず、95分の実行が落ちるとその回の観測が丸ごと消えていた。

### 最後の書き出しでメモリが足りなくなる

作業ファイルを素直に `readCsv` して `sort` すると、行をオブジェクトに開くぶんが効く。
**実測 5,358行で484MB → 20,928行で約1,892MB**。これに観測台帳・入力文字列・出力文字列が
乗るとピークは2.5〜3GBで、この機械の空きメモリ（実測3.0GB／全体15.7GB）を超える。
90分かけた取得の直後に落ちるのが一番もったいない。

`src/intent/finalize.js` は**行をオブジェクトに開かずに並べ替える**。
引用符の状態だけ見て行の範囲を切り出し、並べ替えキーと位置だけを持つ。
最後に元テキストから切り出して流し込むので、ピークは200MB前後で済む（実測5倍速）。

- `No` 列は作業ファイルでは空にしてあり、並べ替えた後にここで採番する（先頭列なので行頭に足すだけ）。
- **架電禁止の判定はここでも行う**。行は追記時にも `toCsv` のガードを通っているが、
  最終書き出しにも関所を置くのが既存の設計。速い経路に替えた時にここを落とすと関所が1枚減る。
- 旧経路との一致は実データで確認済み（行数・ヘッダ・全セルが一致、差分0）。

### 途中で落ちた時の出口

```
npm run intent:finalize    # 作業ファイル → 最終CSV（取得も採点もしない）
```

最後の書き出しだけが落ちた場合、取得済みの作業ファイルは無傷なのでここから作り直せる。
検証: 落ちた想定の作業ファイルから復旧し、正常時の出力と**差分0**。

### 取得マナー

1社あたりの取得は**6ページ**（outline・employment を2卒年ぶん＋sem＋is）。
mynavi 系統と faces 系統で現行卒年の outline/employment が丸かぶりだったので、
1社の処理中は同じURLを二度取らないようにした（9ページ→6ページ）。
並列6・間隔120msは既存ハーベスタ `harvest-icp-wide.js` と同じ設定で、

追加8軸の検知に寄与しなかったため取得しない。

## 軸を増やすと階層の目盛りが伸びる（後から気づいた）

**軸を足すと合計点の目盛りそのものが伸びる**ので、階層の閾値は据え置くと意味が変わる。
実測でA階層（即架電・今週中）が **11% → 25%** に膨らんだ。20,928社の25%＝5,200社は
「今週中に架電」というラベルの意味を失う。原因は2つあった。

1. **face群に群上限を付け忘れていた**。既存の課題群には
   operations32 / conversion32 / complexity24 / purchase40 の上限があるのに、
   追加した5軸（合計重み100）だけ青天井だった。`FACE_GROUP_CAP = { face: 26 }` を追加。
   掲載面が丁寧な会社ほど中身と関係なく上位に来るのを防ぐ。
2. **閾値そのものの引き直し**。A閾値 40 → **48.4**（上限適用後の分布で上位10%）。
   ※上限適用“前”の分位で決めると上限のぶん点が下がって8%になる。一度これで外した。

### 閾値を上げたら設計の約束が壊れた

元の設計は「A＝最強シグナル1本 or 中位2本」。最強シグナル①（人事・採用担当の中途求人）は
重み40なので、閾値48.4では**単独でAに届かなくなった**。最も精度の高い軸が「今週架電」から
落ちるのは設計の後退なので、昇格条件として明示的に戻した。

```
最上位の重み(40)の軸が「確定」で、かつ減衰0.5以上 → 合計点に関わらずA
```

重みを閾値に合わせて水増しするより、昇格条件として書くほうが後から読める。
「確定なら何でも昇格」にすると閾値を上げた意味が消えるので、最上位の重みに限っている。

### 取得し直さずに採点だけやり直す

20,928社の取得に約90分かかるため、重みや閾値を直すたびに取り直していては較正できない。
検知（どの軸がどの強度で立ったか）は取得時に確定していて、スコアはそこからの純粋な計算なので、
採点だけをやり直せる。

```
npm run intent:rescore    # シグナル内訳JSON から スコア/階層/優先度 を再計算（ネットワーク0）
```

検知ルールそのもの（`signals.js` の判定）を変えた場合はこれでは戻せない。取得からやり直す。

## 2周に分ける（広く浅く → 熱い層だけ深く）

最強シグナルの **S1（人事・採用担当の中途求人・重み40）は求人検索でしか立たない**。
求人ボックスは polite.js がホスト単位で直列化するため実測**6秒/社**で、2万社には当てられない。
そこで広い1周目で順番を作り、上位だけに重い系統を当てる。

```
npm run intent:pool        # 統合マスタ → 20,928社
npm run intent:wide        # 21軸のうち掲載面系を全件に（約90分）
npm run intent:deep:pool   # 1周目のA階層から上位800社
npm run intent:deep        # その800社に site（S3/S6/S9-S16）を当てる
npm run intent:deep:jobs   # ↑に加えて jobs（S1）も当てる ※実測では割に合わない（下記）
```

`site` は各社の自前ドメインなので並列が効くが、`jobs` は求人ボックスの1ホストに
直列化される。既定の `intent:deep` から jobs を外してあるのはそのため。

2周目は1周目の結果を消さない。別CSVに出し、観測台帳には同じ社の観測として積む。
1周目で立った軸は台帳に残っているので、2周目のスコアは両方を合算した値になる
（`--no-store` で試すと1周目ぶんが合流せず、実際より低く見えるので注意）。

### jobs系統の実測利回り: A階層38社で S1 は 0社

最強シグナルに期待して2周目を作ったが、**A階層38社に当てて S1 の検知は0件**だった。
検知器そのものは正しく動く（人事ロールの求人票で確定・強度1.0、その社自身の新卒求人は除外）
ことを確認済みなので、単純にこの母集団に「いま人事を中途で募集している会社」が少ない。
0/38 は「3%程度の出現率なら十分あり得る」範囲なので**0%と断定はできない**が、
95%上側信頼限界で約8%＝**2周目のコスト（実測6秒/社）に見合う軸ではない**。

同じ2周目で `site` 系統は S3（採用専用メール）を38社中16社で検知した。
**2周目の価値は jobs ではなく site 側にある**というのが現時点の実測。

## 測って採らなかった系統（プレスリリース）

「幅」を増やす候補として PR TIMES を検討した。社名で1社ずつ引くと2万社には当てられないが、
**キーワードで引いて統合マスタと突合する**なら数十リクエストで済む（robots.txt も検索面を許可している）。

実測（6キーワード・2026-09-14）:

| | |
|---|---:|
| 抽出された企業（のべ） | 211社 |
| 統合マスタに社名一致 | 69社（約40%） |
| うち従業員100-2000名（MOCHICAの主戦場） | **14社** |

一致率だけ見ると悪くないが、**中身が買い手ではない**。実際に一致したのは
ヒューマネージ・ミイダス・PeopleX・ALL DIFFERENT のような人材/HR SaaS 各社、
つまり「採用について発信する側」＝競合と隣接ベンダーだった。

理由ははっきりしていて、**プレスリリースを出す習慣があるのはIT・HR業界とスタートアップ**で、
統合マスタの主体である地方の中堅製造業・卸売業はほぼ出さない。
つまりこの系統は、母集団の中で**最も対象から遠いセグメントに偏って**当たる。

6キーワードで買い手候補14社、しかもその多くが要精査。**採らない判断をした。**
（業種列はマスタの28,129社中3,296社にしかなく、ベンダー自動判定も現状は当てにならない。
将来やるなら業種の充足が前提になる。）

## 使用範囲

検知は入力CSVと指定した取得系統の公開記載に限る。市場全体の網羅性は未検証。
重みは営業仮説であり、受注確率ではない。資料が無い企業は**未検知**であって、
課題が無いことを意味しない。
