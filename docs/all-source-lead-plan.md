# 全データソース・全媒体からリードを作る実装計画

> 作成日: 2026-11-05 ／ 対象: `saiyo_tantousha_poc` のリスト作成系一式
> 目的: まだ手を出していないデータソース・媒体をすべて洗い出し、どのソースからでも同じ品質ゲートを通ってリードが出る構成にする。

---

## 0. 結論

1. **母集団はほぼマイナビ1本足**。統合母集団 `data/leads-consolidated-all.csv`（28,137社）の約8割がマイナビ由来のファイルから来ている。
   `掲載媒体` 列で見ると、求人ボックス 3,219／Wantedly 875／gBizINFO 713／マイナビ 164 で、他の媒体は各3社以下。
2. **110媒体の `data/media-catalog.json` は「プローブ済み・未収穫」**。媒体→企業抽出の出力 `data/media-company-pool.csv` は **3社** しかない。
3. **業種が89%空欄（24,974社）**。ICPは業種が効く（流通小売・金融・介護・機電が勝ち筋、ITは除外）のに、今の母集団ではそのゲートがほとんど効いていない。
4. 未着手のソースは **公的オープンデータ・ハローワーク・地方/業界特化の新卒媒体・マイナビ以外の合説と大学・人名ソース・自社接点** の6系統に大きく分かれる（§2）。
   中でも **介護サービス情報公表のオープンデータ、女性の活躍推進企業DB、gBizINFOの職場情報** の3つは、一括取得できて二次利用もでき、しかもICPの勝ち筋に直結する。最初に着手するならこの3つ。
5. 実装は「媒体ごとにビルダーを1本ずつ書く」のをやめる。**ソースアダプタ（収集だけを書く）＋共通パイプライン（名寄せ→エンリッチ→ゲート→採点→出力→台帳）** に分け、ソースは登録簿に1行足せば乗る形にする（§3）。

## 3. 実装計画

### 3-1. 設計の方針

今は媒体ごとに `build-*.js` が収集からゲート・出力までを抱えている（src 203ファイル、`build-icp-*` だけで8系統）。
経路ごとに除外の集合がずれて既存企業が9割混ざった事故も、この構造から来ている。新しいソースを足すたびにこの事故が起きないよう、**ソースが書くのは「収集」だけ**にする。

```
[ソースアダプタ]  A1 介護 / A2 女性活躍 / B1 ハローワーク / C1 地方媒体 … / 既存のマイナビ・Wantedly …
      │  共通の観測レコード（Observation）を出すだけ
      ▼
[観測ストア]      data/obs/<source>/<YYYY-MM-DD>.jsonl（追記のみ・出典URLつき）
      ▼
[名寄せ]          company-match.js ＋ 国税庁APIで法人番号を確定 → 企業テーブル（項目ごとに出典を保持）
      ▼
[エンリッチ]      gBizINFO（基本＋職場情報）で業種・規模・採用数 → 電話（phone.js）→ 担当者名（harvest 系）
      ▼
[ゲート]          ng-guard → exclusion-index（顧客/BALES/SF/台帳）→ icp-rules → suppression
      ▼
[採点]            mochica-fit v5.1 × 経路の温度（channel-temp）× ソース信頼度
      ▼
[出力]            csv.js の toCsv（NGガード込み）→ format-bales / deliver → 台帳へ自動記録
```

#### 観測レコード（Observation）の契約

```js
{
  source_id: 'kaigo-kouhyou',          // 登録簿のID
  observed_at: '2026-11-05',
  company_name: '社会福祉法人○○会',
  corp_no: '1234567890123',            // 取れれば
  url, phone, pref, industry_raw,
  employees, hire_newgrad, grad_year,  // 取れた項目だけ
  recruiter_name, recruiter_role, recruiter_dept,
  signal: { type: '新規掲載', date: '2026-10-30' },  // 出来事系のみ
  evidence_url: 'https://…'            // 必須
}
```

#### ソース登録簿（`data/source-registry.json`、`media-catalog.json` を拡張）

ソースごとに次を持たせる。**登録時に法務区分と規約確認日を必須にする**。

| 項目 | 例 |
|---|---|
| `id` / `name` / `group` | `kaigo-kouhyou` / 介護サービス情報公表 / A |
| `legal_tier` / `tos_checked_at` | `T1` / `2026-11-05` |
| `method` | `bulk-download` / `api` / `sitemap` / `list-crawl` / `pdf` / `search` / `manual` |
| `cadence` | `semiannual` / `daily` / `weekly` |
| `fields` | `["社","規","電","業"]` |
| `reliability` | 0.0〜1.0（採点のソース信頼度に使う） |
| `icp_prior` | `◎` / `○` / `△` |

#### ソース別スコアカード（`npm run source:kpi`）

各ソースについて、**新規率**（除外マスタ・台帳に無い率）、**ICP適合率**、**電話率**、**担当者名率**、**採用6名以上の確定率**、**納品後の接続率・アポ率**（台帳×BALES/Zoom の突合）を出す。
新しいソースは **200社のパイロット** でこれを測り、続けるか止めるかを決めてから全件を回す。

#### リードの段階を分ける

「担当者名・電話・新卒6名以上」の3条件を満たす名指しリストだけを出口にすると、新しいソースの大半（名前が無い）は捨てられる。そこで段階を持たせる。

| 段階 | 条件 | 出口 |
|---|---|---|
| L0 候補 | 企業を識別できた | エンリッチ待ち |
| L1 適合 | ICPフロア通過（業種・規模・採用数） | 電話・名前のエンリッチ待ち |
| L2 架電可能 | ＋電話 | 採用窓口宛ての架電リスト |
| L3 名指し可能 | ＋担当者名 | 名指しリスト（現行の3絶対条件） |

L1→L2→L3 の昇格を自動のエンリッチキューで回す。どのソースから入っても、同じ順番で太っていく。

| **P3 新卒媒体の横展開** | 4週 | B2〜B4・C1 地方35媒体（CMS型ごとにテンプレ化）→ C2 業界特化 → C3 大手残り → C5 高卒 → C4 口コミ（列挙のみ）。各媒体に `legal_tier` を付けてから着手 | 収穫ゼロの媒体は理由つきで T3 または停止に分類 |
| **P4 イベント・大学** | 2週 | D1（PDF抽出アダプタ）・D2（大学の就職先・学内合説） | 同上 |
| **P5 出来事・人名** | 3週 | G2 求人スナップショットの日次化・G1 他のプレスリリース・G3 導入事例（N6を実装）・G4 ATSテナント・F1〜F4 人名ソース | ホットリードで差分シグナルが発火する |

| P7 有料データ | 判断 | P1〜P3 のスコアカードで穴が残った列についてだけ検討する | 投資判断 |

**並べ方の理由**: 「ICP適合 × 新規率 × 法務の明確さ ÷ 実装コスト」で並べた。
P1 は一括ダウンロードで済むので安く、法務も明確で、勝ち筋の業種（介護・金融・医療）を直接狙える。
P3 の地方媒体は ICP の「地方中堅」に直撃するが、媒体ごとに構造が違うのでコストが高い。テンプレート化で抑える。

### 3-3. 既存コードの扱い

- `polite.js`（robots遵守・ホスト別レート制限・キャッシュ）は全アダプタ必須。
- 名寄せは `company-match.js`、除外は `exclusion-index.js`、ICPは `icp-rules.js`、NGは `ng-guard.js` を**そのまま唯一の入口として使う**。アダプタの中で独自の除外をしない。
- 新しいアダプタでは、`scrape-base.js` にある「人手操作の模倣」による bot 検知の回避は使わない。ブロックされた媒体は T3 として扱う。
- 既存の `build-*.js` は P0 のアダプタ化が済んだものから順に「レシピ（登録簿＋ゲート条件の設定）」に置き換え、旧ビルダーは削除する。

### 3-6. 初回の実測（2026-11-05・全件）

| ソース | 観測 | 名寄せ後 | 新規率 | 既存除外 | NG | IT | L1 | L2 | 備考 |
|---|---|---|---|---|---|---|---|---|---|
| kaigo-kouhyou | 72,589 法人（22.3万事業所） | 70,287 | 86.5% | 8,772 | 2,289 | 0 | 0 | 1,346 | 法人番号95%・電話100%。拠点10以上だけが L2 に上がる |
| kenko-keiei | 26,838 法人 | 26,838 | 64.5% | 9,167 | 1,120 | 565 | 483 | 109 | 中小規模部門（2.3万）は規模が分からず L0。L2 は介護と合流した分 |

- 2ソース合流の出力 `data/leads-src-kaigo-kouhyou+kenko-keiei-2026-11-05.csv` は **L2 以上 1,346社**。
  `audit-leak` PASS（被り0・自己重複0）、NG該当0、既存母集団（未納品）との重なり57社。
- 健康経営の一覧は既存母集団の **5,973社と一致し、うち5,172社は業種を埋められる**（空欄率89%→約70%）。
- 実データで見つけて直したこと:
  - 同名の別法人（法人番号が違う）を社名一致で1社に合流していた → 法人番号が食い違えば別会社にする
  - 既存母集団とマスタを1つの索引に混ぜると、母集団への社名一致がマスタへの表記ゆれ一致を隠す（17件漏れ）→ 索引を分けた
  - `audit-leak` は同名を自己重複と数える → 出力時に上位の1社だけ残し、残りは除外明細に「同名の別法人」で残す
- 次に効くもの: **`GBIZ_TOKEN`**（健康経営の中小規模2.3万社と介護の L0 に従業員数を入れて L1 へ上げる）、
  **電話の補完**（健康経営 L1 の483社は電話だけが無い）、拠点数の閾値（`--min-sites`、既定10）の妥当性をアポ率で検証。

**新しいソースの足し方**: ①`registry.json` に1行（`legal_tier`・`tos_checked_at` 必須）→ ②`src/sources/adapters/<id>.js` に
`collect(ctx)` を書く（観測レコードの配列を返すだけ。除外・採点はしない）→ ③`test/sources.test.js` に純ロジックのテスト →
④`npm run src:kpi -- <id> --pilot 200` で続けるか止めるかを決める。

## 4. 運用・法務のルール

1. **T3（ログイン壁・規約禁止・robots不可）は収集しない**。登録簿に `legal_tier` と `tos_checked_at` が無いソースは、パイプラインが受け付けないようにする。
2. 担当者名は、業務上の連絡先として公開されているものに限る。全件に出典URLを保存する。
3. オープンデータは各サイトの利用規約に従う（介護サービス情報公表は利用時に一報を入れる）。
4. すべての出力は `toCsv()` を通す（NGガード）。納品前に `npm run ng:check` が 0本/0行 であることを確認する。
5. 日次・週次のソースは Windows タスクスケジューラに登録する。登録簿の `cadence` からジョブを生成する。
