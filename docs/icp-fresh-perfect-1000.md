# 完全新規 × ICP完全適合 1000件リスト（2026-08）

`data/leads-icp-fresh-perfect-1000.csv` … 営業がそのまま架電できる納品ファイル。
並びは **① 採用担当者名あり → ② 代表者名あり → ③ 名前なし**、各ティア内はアポ期待度の降順。

## 1. ICP完全適合の定義（全1000行が5条件すべてを実データで充足）

| # | 条件 | 判定に使った一次情報 |
|---|---|---|
| ① | 完全新規 | 統合マスタ30,290社 ＋ BALES 22,892社 ＋ MOCHICA顧客430社 ＋ SF全リード86,674件（正規化社名 67,380件）に不在 |
| ② | 新卒採用インテント | マイナビ新卒の掲載を実スクレイプで確認（`掲載媒体=マイナビ`／`採用ページURL`が実在の企業ページ） |
| ③ | 規模フィット | **会社概要ページの従業員数** が 100〜2000名（中央値248名） |
| ④ | 非IT | **会社概要ページの業種ラベル** で IT/ソフトを絶対除外（`icp-rules.js`） |
| ⑤ | 到達性 | 電話番号が日本の電話番号として妥当（`normalizeJpPhone`） |

`採用フロア`列は icp-rules の「年間新卒6名以上」を可視化したもの。媒体が採用予定人数を出さない社が
あるためハード条件にはせず、判明分だけ `充足(N名)` / `未充足(N名)` / `不明` を表示する。

## 2. 今回わかった重要な事実（次回の前提になる）

### 2-1. 「マイナビ母集団の上限」は誤りだった — discoveryが1ページ目しか見ていなかった
v1 は `discoverCorpIds` で検索結果の**先頭100社**だけを収穫していた。実際は
「食品」= 6,150社ヒット。つまり母集団の 1.6% しか見ていなかった。
→ `discoverCorpIdsPaged`（「次の100社」を辿る）と、汎用語で全社を列挙する `mynavi-corpus.js` を追加。
**マイナビ2028の全掲載企業は 30,016社**（`data/mynavi-2028-corpus.csv`）。ここが真の母集団の底。

### 2-2. v1プールには ICP違反が19%混ざっていた
従業員数を本文の自由文マッチで拾っていたため誤読していた（例: すかいらーくグループを「533名」と
記録。会社概要の実値は 正社員5,779名／クルー98,327名＝規模帯外）。業種列は空のままで
**非IT条件が判定されずに素通り**していた。
→ `verify-icp-legacy.js` で757社を会社概要ページから引き直し、**144社を不合格**（IT/ソフト124社・
規模帯外13社・従業員数不明7社）。`extractOutlineFacts` はラベル行の次ブロックを構造で読む方式に変更。

### 2-3. 氏名の取得経路：実測の歩留まり（今回の1000件で計測）
| 経路 | 実測 | 備考 |
|---|---|---|
| **マイナビ 別卒年ページ**（`enrich-mynavi-crossyear.js`） | **採用担当者名 +132／962社照会（13.7%・別社スキップ201を除くと17.3%）** | ティア1の主力。27卒/28卒で問合せ先の中身が違い片方だけ実名が出る。corpIDは卒年をまたいで安定（h1で同一社を必ず突合） |
| マイナビ 3パターン抽出（スクレイプに内包） | 約5-8% | 伝言板の名乗り／インタビュー帰属／問合せ先 |
| **自社サイト深掘り**（`probe-site-deep`） | **代表者名 +85／271社（31%）**・採用担当者名 +5（1.8%） | ティア2の主力。会社概要ページの代表者名は取れるが採用担当者名はほぼ出ない |
| gBizINFO 代表者名 | 代表者名 +49／654社（7.5%）・公式URL +73社 | 社によってデータ自体が無い。※クエリは要注意（2-4） |
| Wantedly | **到達不能** | 2026-08時点で未ログインの企業検索が不可。ICPとの交差も0社（2-5） |

**メール推定の氏名は納品しない**: 採用メールのローカル部から起こした姓（`honda@tanakaseiko.co.jp` → 本田）は誤名率が高く「参考」止まりというユーザー方針（2026-07）に従い、`finalize-icp-1000.js` が氏名欄から自動降格する（今回3件）。同スクリプトは問合せ先の分解で部署に社名が食い込んだ行（今回7件）も修復する。

### 2-4. gBizINFO のクエリは「法人格を外した核」で引く
`name=株式会社クックマート` → **404** / `name=クックマート` → **200**。
v1の代表者名補完が17%止まりだった一因。`mkey()`（注記・法人格を落とした突合キー）で引き、
候補側も同じキーで完全一致だけ採る（誤マッチ0）。ただし 2-3 のとおり gBiz は代表者名自体を
ほとんど持っていないため、伸びしろは小さい（実測 7.5%）。ただし公式URLが取れる（累計194社）ので、
そのURLを 2-3 の自社サイト深掘り（代表者名31%）に渡す前段として価値がある。

### 2-5. Wantedly は未ログインでは企業検索できない（方針: ログイン突破はしない）
- `projects?q=社名` … 社名を無視した推薦結果が返る（会社一致ガードで100% company-mismatch）
- `companies?q=社名` … ログイン壁（Playwrightでも本文1,242バイトのみ）
- 唯一動くのは sitemap ハーベスト（`harvest-wantedly.js`・募集ページから投稿者名を刈る）だが、
  取れるのはIT/スタートアップ中心で、**本ICP（非IT・100-2000名）との交差は0社**。
規約リスクのためログイン突破は実装しない（`workspace-and-manual-research-layer` の方針を踏襲）。

## 3. 再現手順

```bash
npm run mynavi:corpus   # ① マイナビ全掲載企業を列挙 → data/mynavi-2028-corpus.csv
npm run icp:verify      # ② 既存プールを会社概要で再検証 → data/icp-legacy-verified.csv
ICP_V2_CORPUS=data/mynavi-2028-corpus.csv ICP_V2_TARGET=600 npm run icp:v2   # ③ 完全新規だけ総当たり
npm run icp:final       # ④ ICP5条件を再判定して1000件に組み立て＋サマリ生成
npm run icp:crossyear   # ⑤ 別卒年から採用担当者名を上積み（任意・最有力）
npm run icp:names       # ⑥ gBiz代表者名＋自社サイト会社概要から代表者名を上積み（任意）
npm run icp:finalize    # ⑦ 卒年をURLから確定・メール推定氏名の降格・部署の修復・最終検証・サマリ再生成
```

**⑦は氏名エンリッチの後に必ず1回実行する**（ICP5条件を納品ファイル自体に対して再検証し、違反が1件でもあれば異常終了する）。

同時に走らせる Playwright セッションは **2つまで**。3セッション以上を job.mynavi.jp に当てると
エラーページが返り、ページ送りが途中で止まる（実測）。
