## なぜ効くか

MOCHICAは新卒ATS。中途が採用計画の主で、その横に新卒枠が少しあるだけの会社は、
担当者の感触が良くても新卒側に割り当てられた予算が小さく、決裁まで届かない。
逆に新卒が主戦場の会社は、新卒の歩留まりがそのまま事業計画に響くので話が前に進む。

判定を **ICP側（icp-rules.js）に置き、シグナル側がそれを呼ぶ**構造にしてある。
リストに載る条件（ゲート）と刺す順（S30）が別々の定義に分かれてずれるのを防ぐため。

## 単位が揃わないことを隠さない

| | 取れるもの | 出所 |
|---|---|---|
| 新卒 | 募集**人数** | 卒年面の募集人数 → 定着率開示欄の直近入社実数 → 掲載の採用予定人数 |
| 中途 | 公開中の求人**件数** | 求人ボックスの社名一致カード |

中途の採用“人数”は公開されていない（新卒と違って募集人数を出す慣行がない）。
1件の求人が何人採るかは分からないので、**等倍では比べない**。

```
中途件数 ≤ 新卒人数                                   → 新卒中心
中途件数 ≥ 新卒人数 × 2 かつ 5件以上                  → 中途中心（ICPから落とす）
その間                                                 → 併用
```

倍率と最低件数は `ICP_MIDCAREER_RATIO_MAX` / `ICP_MIDCAREER_MIN_COUNT` で変えられる。
根拠文には必ず件数と人数を並べて書き、「単位が違う」と明記している。

## 実測で踏んだ落とし穴（そのまま仕様になっている）

### ① 「中途0件」を新卒中心の証拠にしてはいけない

求人ボックスは**全社横断の関連度順**で、1ページ目がよその会社のカードで埋まると
その社は出てこない。

> 実測 2026-09-18・日本無線(株): 「日本無線 中途採用」で25枚返るのに、社名一致は**0枚**。
> 25枚の中身は日本無線硝子・古野電気・豊田合成など。

ここを「中途0件＝新卒中心（確定）」と数えると、中途を大量に募集している社が最上位に化ける。
そこで **社名一致カードが1枚も無い回は「0件」ではなく「未取得」**として扱い、構成は不明にする。
件数を信じるのは「その社のカードが少なくとも1枚は索引に出た」ときだけ。

### ② その社自身の新卒求人を中途として数えない

求人ボックスは「2027 新卒採用 コンピュータ・通信機器」のようなカードを大量に返す。
新卒語・アルバイト/派遣/インターンの枠は件数から落とす。

### ③ マイナビ掲載本文から「新卒寄り」を読んではいけない

件数が取れない社への弱い当て方として、採用ページの新卒語/中途語の量を見る経路がある。
ここで**マイナビの掲載本文を混ぜると、構造上100%新卒なので全社が新卒寄りになる**
（実測8社中8社が「新卒寄り」になり、S30が7社で立った）。循環なので、
寄りを読むのは**自社サイトの採用ページ本文（`ev.自社サイト本文`・site 系統）だけ**にしてある。

### ④ 語の量だけで「中途中心」と断定しない

寄りは件数ではない。新卒寄りのときだけ「新卒中心（弱）」と言い、中途寄りでも**不明のまま**にする。
ICPのゲート（母集団から落とす判断）に足る証拠ではないため。

### ⑤ 社名の但し書きは検索語から外す

「(株)メーカーズ【K-cafe】」「【東証プライム上場】」をそのまま投げると求人ボックスが404を返す
（実測8社中3社）。緩めるのは**検索語だけ**で、突き合わせは元の社名の完全一致のまま。

## S30 の強度

| level | 条件 |
|---|---|
| 確定 | 新卒人数 ≥ 中途件数 × 2 |
| 強 | 新卒人数 ≥ 中途件数 |
| 弱 | 件数は未取得だが、自社サイトの採用ページが新卒寄り |

重み26・半減期210日・群上限26（mix群は1軸）。
**中途中心の社では減点シグナルを作らない**（資金リスクと同じ方針）。落とすのはICPのゲートの仕事。

## 取得カバレッジ（正直な現状）

`--sources csv,mynavi,faces,site,midjobs` で無作為8社を流した実測:

| 結果 | 社数 |
|---|---|
| 新卒中心（確定・件数あり） | 3 |
| 不明（求人ボックスに社名一致カードが出ない／自社サイトが新卒・中途の併記） | 5 |
| 中途中心 | 0 |

**中途件数が取れるのは一部**で、残りは不明のまま通る（落とさない）。
つまりこのゲートは「中途中心を確実に排除する」ものではなく、
「**中途中心と分かった社を確実に排除する**」もの。不明の社は `要確認項目` に
`中途採用の規模(midjobs未取得)` として出るので、そこを埋めれば精度が上がる。

`midjobs` は求人検索エンジンへの問い合わせが1社あたり最大2回増える（polite.js がホスト単位で
直列化する）。全数ではなく、絞り込んだリストに対して回す想定:

```
npm run intent:mix     # intent-pool-deep.csv に対して csv,mynavi,faces,midjobs
```

## ICP v5.1 側の変更

[icp-scoring-v5.md の §7](icp-scoring-v5.md) に書いた。要点だけ:

1. **絶対条件⑥** に採用構成を追加（中途中心・新卒なしだけ落とす）
2. **入力の充填** `resolveIcpInputs()` — CSVが空でも掲載面から従業員数・新卒人数を埋める。
   欠測が減るぶん、従来「不明だから通す」で膨らんでいた要確認・適合の判定が動く
3. **第2段に採用構成の係数**（新卒中心 ×1.15 / 中途中心 ×0.55）。
   **これだけは実測フィットではなく製品適合の仮説**なので `factors.仮説` に分けて返し、
   `ICP_V5_MIX=off` で v5.0 の採点に戻せる
